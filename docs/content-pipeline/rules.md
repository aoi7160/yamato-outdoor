# 記事制作パイプライン 共通ルール

全エージェント(企画・調査・執筆・トンマナ確認・事実確認・最終チェック)が、
作業を始める前に必ず読むファイル。**ここに反する出力は、どれだけ文章が良くても不合格。**

優先順位: `CLAUDE.md` > `docs/persona.md` > **このファイル** > `docs/tone-and-manner.md` > `docs/content-pipeline/style-guide.md`

---

## R1. 実体験の境界(最重要)

このメディアの価値は「運営者が実際に使った・歩いた」ことにある。
AIが体験を書いた瞬間に、メディアの存在理由が消える。

### R1-1. AIが書いてよいもの / 書いてはいけないもの

| 書いてよい(AIの仕事) | 書いてはいけない(運営者の仕事) |
|---|---|
| 出典のある事実(仕様・歴史・標高・営業期間) | 実測値(重量・時間・気温・距離・サイズ) |
| 出典のある事実から導ける一般的な説明 | 山行の場面(日付・天候・路面・同行者・時刻・何が起きたか) |
| 構成・見出し・表・比較の枠組み | 感覚(痛い・楽・蒸れた・滑った・重かった) |
| 読者の疑問の整理 | 書き手の行動・習慣(「私は〜している」「実践している対策」) |
| 運営者の回答の**言い換え・整理** | 書き手の判断の理由(「私が〜を選んだのは〜だから」) |
| 【要実体験】の目印と、何を書けばよいかの案内 | 比較体験(「別の靴で同じ道を歩くと〜」) |
|  | 写真・キャプションの撮影条件 |
|  | 書き手のプロフィール上の事実(登った山・登山歴・頻度) |

### R1-2. 「言い換え」と「付け足し」の線引き

運営者の回答(取材シート・実体験記録)は**素材**であって、**下書きではない**。
言い換え・語順の入れ替え・要約はしてよい。**情報を足してはいけない。**

足してはいけない情報の種類:

- **数量**(深さ・時間・回数・距離・サイズ・何分歩いた)
- **状況**(前日の天気・路面の状態・場所の特定・時間帯)
- **原因**(「〜だったのは、〜が原因だった」)
- **感覚の具体化**(「楽だった」→「膝まで衝撃が来なかった」は付け足し)
- **頻度・継続**(「いつも」「毎回」「一度も〜ない」「今のところ」「履き込んで」)
- **比較**(他の道具・他の山・以前の自分との比較)
- **心情の描写**(「早く終わってほしいと思う下りにはならなかった」)

**判定テスト:** 体験を述べた文ごとに、「この情報は運営者の回答のどこに書いてあるか」を
指させるか確認する。**指させない情報が1語でも入っていたら、その部分を【要実体験】に置き換える。**

```
運営者の回答: 「雨の日に着たが蒸れなかった」

✗ 付け足し
  梅雨の六甲を3時間歩いたが、背中までさらっとしていた。
  (梅雨・六甲・3時間・背中・さらっと、はどれも回答に無い)

○ 正しい下書き
  雨の日に着て歩いても、蒸れは気にならなかった。
  【要実体験：歩いた山・時間・気温など、具体的な状況があれば記入】
```

### R1-3. 継続使用をにおわせない

使用回数・使用期間は、運営者が明記を指示しない限り**書かない**。
同時に、**書かれていない継続使用を示唆する表現も使わない。**

| 使わない(事実でない限り) | 理由 |
|---|---|
| 履き込んで / 使い込んで / 愛用している | 長期使用の示唆 |
| 何度も / いつも / 毎回 / 季節を問わず | 複数回の示唆 |
| 〜してから、一度も〜ない | 複数回の示唆 |
| 今のところ〜ない | 継続使用の示唆 |
| 〇年使った / 〇シーズン | 数字は運営者の記入のみ |

`docs/persona.md` Editorial Policy 1「使ってから書く。最低3回」との関係は、
**企画エージェントが着手判断で確認する**(R1-5)。執筆段階で回数を盛って辻褄を合わせない。

### R1-4. 一般論で体験を代用しない

体験が足りないとき、「一般に〜と言われる」で埋めない。
一般論は出典付きの事実として書くか、書かない(`docs/tone-and-manner.md` 1「体験と一般論を混ぜない」)。

### R1-5. 目印の書式

```
【要実体験：〇〇を記入】
```

- 〇〇には**何を書けばよいか**を具体的に書く(「感想を記入」ではなく
  「下りで足首がぐらついたか、どの区間だったかを記入」)
- 目印は本文中のその位置に置く。末尾にまとめない
- 実測値の目印は `【要実体験：実測重量(片足・サイズ26.5cm)を記入。キッチンスケールで量る】` のように、測り方まで書く
- 写真は `<!-- 【要実体験：写真】何が写っていればよいか / alt案 -->` のHTMLコメントで置く
- 事実の確認が取れない数字は `【要確認：〇〇】`(R2-4)。体験の目印と混ぜない

**目印が1つでも残っている記事は「公開待ち」にしない。**

## R2. 事実と出典

### R2-1. 出典が要るもの

重量・寸法・価格・標高・距離・コースタイム・営業期間・発売年・創業年・
素材名・技術名・法令・統計、および固有名詞の正式表記。

### R2-2. 出典表(設計書に必ず置く)

| 主張(本文の文) | 値 | URL | ソース種別 | 確認方法 | 確認日 |
|---|---|---|---|---|---|
| X ULTRAは2012年に登場 | 2012年 | https://… | 一次(メーカー) | ページを開いて本文を確認 | 2026-10-11 |

- **ソース種別:** 一次(メーカー公式・自治体・公的機関・施設公式)/ 二次(大手専門媒体)/ 三次(個人ブログ・まとめ・Q&A)
- **確認方法:** 「ページを開いて本文を確認」/「検索結果の要約のみ」
- 価格は `(2026年10月時点)`、カタログ重量は `(カタログ値・サイズ〇〇)` を本文にも併記する

### R2-3. 採用基準

| 状況 | 扱い |
|---|---|
| 一次ソースのページを開いて確認した | 書いてよい |
| 二次ソースのみ | 書いてよいが、本文で断定しすぎない |
| 三次ソースのみ | **書かない。** 書くなら運営者の判断を仰ぐ(【要確認】) |
| 検索結果の要約だけで、ページ本文を読んでいない | **未確認扱い。書かない** |
| 複数のブログで同じことが言われている | 「傾向」でしかない。事実として断定しない |
| ソース同士で値が食い違う | 一次ソースを採用し、食い違いを設計書に残す |

### R2-4. 確認できない数字

書かない。どうしても必要なら `【要確認：〇〇の値。候補は△△(出典：三次)】` を残し、
最終チェックで運営者に回す。**推測した数字を断定形で書くことは、どんな理由でも禁止。**

### R2-5. 鮮度

営業期間・価格・ロープウェイの運休・登山道の通行止めは変わる。
「〇年〇月時点」を本文に書き、設計書に確認日を残す。

## R3. 独自性(他サイトをなぞらない)

1. **見出しは「読者の疑問」から作る。** 手順は必ずこの順:
   1. 想定読者(`docs/persona.md` P1)がこのキーワードで検索する直前に抱えている疑問を、先に10〜20個書き出す
   2. その後でSERP・関連する質問・競合記事を見て、**答え合わせ**をする
   3. 競合が**答えていない疑問**に印を付ける。そこが記事の存在理由
2. 競合記事の見出し構成を並べて書き換える方法は禁止。
3. 競合記事の文章を要約・言い換えて本文にしない。事実だけを一次ソースから取る。
4. 全モデル・全ルートの網羅(カタログ型)を目指さない。**選び分けの軸**を出す。

## R4. microCMSへの保存

- **下書き(`status=draft`)としてのみ保存する。** 公開APIを呼ばない。公開ボタンは運営者だけが押す
- 既存記事を上書きしない。同じスラッグが既にあれば止めて運営者に聞く
- 本文は `contentHtml`(テキストエリア)に入れる。`content`(リッチエディタ)は空のまま
  (`docs/microcms-schema.md`「本文フィールド」)
- FAQは本文に書かず `faq` フィールドへ。構造化データ(JSON-LD)を本文に書かない
- レビュー記事は `reviewItem` / `reviewBrand` / `reviewRating` を設定する。
  **`reviewRating` はAIが決めない。** 運営者の評価が無ければ空にして、運営者確認事項に載せる

---

## R5. 広告・PR表記

- **アフィリエイトリンクはAIが勝手に入れない。** 入れるかどうかは運営者が決める
- アフィリエイトリンク(`src/lib/article.ts` の `AFFILIATE_HOSTS` に該当するドメイン)が
  1本でも入る記事は、冒頭(リード文より前)に必ず置く:

```html
<p class="pr-notice">※ 本記事にはアフィリエイトリンクを含みます。報酬の有無で評価は変えていません。</p>
```

- 景品表示法(ステルスマーケティング規制、2023年10月施行)。詳細は `docs/analytics.md` 6-3
- メーカーからの提供品・貸与品を使った場合は、その旨を本文に書く(運営者に確認する)

---

## R6. 外部送信・埋め込み

- 記事本文に `<script>` / `<iframe>` / 外部の埋め込み(地図・SNS・動画)を入れない
- 必要だと判断したら、運営者への確認事項として**提案だけ**する
- 計測タグを足す変更は記事制作の範囲外。`CLAUDE.md`「計測タグの約束」に従い、別作業として扱う

---

## R7. 書き手と媒体の約束

- 一人称は「私」。「筆者」「当サイト」は使わない
- 書き手のプロフィール(`.profile`)に書く事実は、`src/layouts/ArticleLayout.astro` の
  著者情報と `/about` に書かれていることだけ。**登った山の名前を足さない**
- 他ブランド・他メディアを批判しない
- `docs/persona.md`「使わない語」を使わない
- 「合わなかった点」を良い点と同じ分量で書く。ただし**合わなかった点も体験なので、
  運営者の回答に無ければ【要実体験】**

---

## R8. 迷ったとき

推測で決めない。設計書の「運営者への確認事項」に書いて、その項目は先に進めない。
**止まることは失敗ではない。推測で書いた1文が、記事全体の信用を壊す。**
