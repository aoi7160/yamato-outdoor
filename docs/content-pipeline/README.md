# 記事制作パイプライン 設計書

> **状態: 承認待ちの案。** 運営者の承認と「10. 決定事項」が埋まるまで `main` にマージしない。
> 自動実行・microCMSへの書き込みは、まだ組み込んでいない。

コンテンツマップに沿って記事の下書きを1本ずつ作り、品質を一定に保ったまま
「公開待ち」の手前まで進める仕組み。運営者の作業を
**取材シートに答える → 運営者シートの目印を埋める → 公開ボタンを押す** の3つに絞る。

---

## 1. 全体像

```
運営者                     パイプライン(/article-pipeline で1記事ずつ)
───────                   ─────────────────────────────────────────
                           1 企画      コンテンツマップから1本選ぶ
取材シートに答える  ←──── │          不足している実体験を取材シートにする
                           2 調査      読者の疑問 → 検索で答え合わせ → 出典 → 見出し構成
                           3 執筆      設計書と取材シートの回答だけで書く。無い体験は【要実体験】
                           4 トンマナ  基準書・修正記録と照らして言い回しを直す
                           5 事実確認  数字は出典と、体験は取材シートと照合する
                           6 最終      チェックリストで合否 → 合格/保留だけ microCMS に下書き
運営者シートを見て  ←──── │          運営者シート(埋める箇所・撮る写真・確認事項)
目印を埋める・撮る
公開ボタンを押す
/article-learn      ────→ 公開版との差分から修正を記録 → 次の記事の基準書に反映
```

## 3. フォルダ構成

### 3-1. 何を公開リポジトリに置かないか

リポジトリはpublicなので、次のものを置くと**公開前に誰でも読める**。

| 置かないもの | 理由 |
|---|---|
| 未公開の下書き(`content/pipeline/`) | 公開前の記事が読める。競合に先に構成を取られる |
| コンテンツマップ(検索ボリューム・優先度) | 事業上の計画そのもの |
| 運営者の実体験記録(装備台帳・山行記録・使用回数) | 私的な情報。記事に書かない判断をした情報も含む |
| 取材シートの回答 | 同上 |

### 3-2. 編集用の非公開リポジトリ(D1で決定)

```
yamato-outdoor(public)                  ← いまのリポジトリ。サイトのコードと公開してよいルール
├─ .claude/agents/article-*.md          ← 6エージェントの指示文
├─ .claude/skills/article-pipeline/     ← 1記事分を回す手順
├─ .claude/skills/article-learn/        ← 公開後の学習
├─ docs/content-pipeline/
│   ├─ README.md                        ← この設計書
│   ├─ rules.md                         ← 全エージェント共通の絶対ルール
│   ├─ style-guide.md                   ← トンマナ基準書(基準記事からの抽出)
│   └─ correction-log.md                ← 運営者の修正記録(書き方だけ。体験の中身は書かない)
└─ docs/articles/<スラッグ>.md           ← 公開後の設計書(公開済み記事のみ)

yamato-outdoor-editorial(private・新設) ← 編集作業の場所
└─ content/
    ├─ content-map.md                   ← コンテンツマップ兼キュー(状態を持つ)
    ├─ experience-log.md                ← 運営者の装備台帳・山行記録・実測値
    └─ pipeline/<スラッグ>/
        ├─ interview.md                 ← 取材シート(運営者が答える)
        ├─ 00-brief.md                  ← 企画
        ├─ 01-design.md                 ← 設計書(出典表つき)
        ├─ 02-draft.md / 02-draft-selfcheck.md
        ├─ 03-styled.md / 03-style-notes.md
        ├─ 04-checked.md / 04-factcheck.md
        ├─ 05-final-check.md
        ├─ 06-operator-sheet.md         ← 運営者向けの1枚
        └─ 90-published.html            ← 公開版(学習用)
```

Claude Code のセッションに2つのリポジトリを入れて動かす。

- **セッションは `yamato-outdoor`(public)から始める。** エージェントとスキルは public 側の `.claude/` にあるため
- 非公開リポジトリは、public 側と**同じ階層**にcloneする。指示文はすべて `../yamato-outdoor-editorial/content/` を作業フォルダとして参照している
- セッションの開始時に非公開リポジトリを選べなければ、「`yamato-outdoor-editorial` も追加して」と頼めば追加できる。
  `/article-pipeline` も、作業フォルダが無ければ追加とcloneから始める

### 3-3. 下書きの形式

`02-draft.md` 以降は「YAMLのフロントマター(タイトル・スラッグ・概要・カテゴリ・タグ・faq・review系)
+ 本文はHTML」。本文をMarkdownにせずHTMLにしたのは、microCMSの `contentHtml` にそのまま入り、
変換の工程(=崩れる箇所)を挟まないため。GitHub上でもHTMLのままある程度読める。

## 4. エージェントと受け渡し

| # | 役割 | 指示文 | 入力 | 出力 |
|---|---|---|---|---|
| 1 | 企画 | `.claude/agents/article-planner.md` | content-map / experience-log | `00-brief.md` `interview.md` |
| 2 | 調査 | `.claude/agents/article-researcher.md` | 00 / interview | `01-design.md` |
| 3 | 執筆 | `.claude/agents/article-writer.md` | 01 / interview | `02-draft.md` `02-draft-selfcheck.md` |
| 4 | トンマナ確認 | `.claude/agents/article-style-editor.md` | 02 | `03-styled.md` `03-style-notes.md` |
| 5 | 事実確認 | `.claude/agents/article-fact-checker.md` | 01 / interview / 03 | `04-checked.md` `04-factcheck.md` |
| 6 | 最終チェック | `.claude/agents/article-final-checker.md` | 00〜04 | `05-final-check.md` `06-operator-sheet.md` |

- 順番の制御・やり直し・差し戻し(2回まで)は `.claude/skills/article-pipeline/SKILL.md`
- エージェント同士は会話しない。**ファイルだけで受け渡す**(後から全工程を追える・試運転で見せられる)
- 体験のチェックは二重にしている:執筆担当の自己点検(02-selfcheck)と、事実確認担当の照合(04)

### 4-1. 体験を守る仕組み

AIは運営者の短い回答を「読みやすく」膨らませる過程で、回答に無い状況・数量・感覚を
自然に足してしまう。文章としては良くなるほど、混ざったことに気づきにくい。そこで:

1. 体験の材料は**取材シート1か所**に限定(チャットのやりとりを材料にしない)
2. 執筆担当は、体験の文ごとに取材シートの回答を引用して対応付ける
3. 事実確認担当が、同じ対応付けを独立にやり直す(`rules.md` R1-2 の判定テスト)
4. 継続使用をにおわせる語は、回答に根拠が無ければ機械的に削る(R1-3)

## 5. 状態の流れ(コンテンツマップの「状態」列)

```
未着手 ─→ 制作中 ─┬─→ 公開待ち ───→ 公開済み   (目印ゼロで最終チェック合格)
                   ├─→ 実体験待ち ─→ 公開待ち   (下書き完成、目印あり。運営者が埋めたら移る)
                   └─→ 制作中(停止) (差し戻し2回超・確認事項で停止)
取材待ち ─→(取材シートが埋まったら)─→ 制作中
```

**「実体験待ち」の記事は「公開待ち」に入れない。**

### 5-1. 目印のまま公開されるのを防ぐ安全装置(提案)

ビルド時に、本文に `【要実体験` または `【要確認` が残っている記事を**ページにしない**
(ビルドログに警告を出す)。microCMSで誤って公開ボタンを押しても、目印入りの記事は世に出ない。
`src/pages/[genre]/[category]/[slug].astro` に数行足すだけ。承認後に実装する。

## 6. microCMSへの下書き保存の方法(選んでください)

いまのAPIキーは**読み取り専用**(`docs/workflow.md` の方針どおり)。下書きを書き込むには、
`articles` への **POST/PATCH だけを許可した別のキー**が要る。公開サイトのビルドには使わない。

| 案 | 仕組み | 準備 | 長所 | 短所 |
|---|---|---|---|---|
| **A. 手動で貼る** | 運営者シートの末尾に「貼り付け用」の値を出す。運営者がmicroCMSに貼る | なし | すぐ始められる。書き込みキーが不要 | 1記事5分ほどの手作業 |
| **B. GitHub Actions** | 最終チェック合格のファイルがpushされたら、Actionsが下書きとして登録 | 書き込みキーをGitHubのSecretsに登録。ワークフロー1本 | キーがAIのセッションに渡らない。Actionsは通信制限が無い | 初期設定が少し要る |
| **C. エージェントが直接登録** | パイプラインの最後にAPIを呼ぶ | 書き込みキーを実行環境の環境変数に。microCMSへの通信を許可 | 最も自動 | キーをAIの実行環境に置く。いまの環境は通信が遮断されている |

**推奨: 試運転はA、軌道に乗ったらB。**

## 7. 実行方法(選んでください)

### 7-0. どの方法でも必要なこと:通信の許可

調査と事実確認は、**メーカー公式・自治体などのページを開いて数字を確かめる**ことが前提(`rules.md` R2)。
いまの Claude Code on the web の環境は外部への通信がほぼ遮断されていて、ページを開けない。
このままだと、事実の大半が「要確認」になる。次のどれかが要る。

- Claude Code on the web の環境設定で、ネットワークアクセスを広げる
  (設定方法: https://code.claude.com/docs/en/claude-code-on-the-web)
- 自分のPCの Claude Code(CLI・デスクトップ)で動かす(通信制限なし)

### 7-1. 選択肢

| 案 | 動かし方 | 週の手間 | 準備 | 向いている状況 |
|---|---|---|---|---|
| **1. 手動コマンド** | 好きなときにセッションを開いて `/article-pipeline` | 起動の1分+結果を見る時間 | なし(通信の許可だけ) | 試運転〜最初の数本。**まずこれ** |
| **2. 定期実行(Routine)** | Claude Code の Routine で毎週◯曜◯時に新しいセッションを起動し、`/article-pipeline` を実行。終わったら通知 | 通知を見て運営者シートを開くだけ | Routineの作成(こちらで設定可)、通信の許可 | 品質が安定したあと。**週1本ペースの本命** |
| **3. GitHub Actions + Claude Code** | Actionsのスケジュールで実行 | 2と同じ | AnthropicのAPIキー(従量課金)、Secrets、ワークフロー | Routineが使えない場合 |
| **4. 自分のPCで定期実行** | PCのスケジューラから Claude Code を起動 | 2と同じ | PCが起動している必要あり | 環境を手元で完結させたい場合 |

**推奨: 1で試運転 → 3〜5本で問題が出なければ2(毎週1本)。**
1本あたりの処理は、調査で数分〜十数分、全体で30分前後を見込む(試運転で実測する)。

## 8. 学習のループ

記事を公開したら `/article-learn <スラッグ>`。

1. 公開版(`90-published.html`)とAIの最終下書き(`04-checked.md`)の差分を取る
2. 運営者が埋めた実体験 → `experience-log.md`(次の企画判断に使う)
3. 運営者が直した言い回し・構成 → `correction-log.md`
4. 2記事以上で同じ指摘が出たもの → `style-guide.md` / `tone-and-manner.md` / エージェント指示文への反映を提案。**運営者の承認後に反映**

---

## 9. 試運転の進め方

1. 10の決定事項を埋める
2. 運営者が `experience-log.md` に、手持ちの装備と最近の山行を書く(10分程度)
3. 1本目を `/article-pipeline <候補> --trial` で実行。**全工程の出力を運営者に見せる**
4. 運営者がフィードバック → 指示文・基準書を直す
5. 問題がなければ、7で選んだ方法で継続運用に移る

1本目の候補は、運営者の山行記録が既にある記事(コンテンツマップ案の判断メモ参照)が向いている。
体験の材料がそろった状態で、パイプライン本来の出来を確かめられるため。
