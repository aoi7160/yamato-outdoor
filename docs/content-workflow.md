# 記事制作フロー

目的: 平日は1日20分以内のチャット確認だけで回り、週末に実体験・写真を足して公開まで持っていく仕組み。
2026年8月は「今月中に10本公開」を目標にした加速スケジュールとして運用する。

## 役割分担

| 曜日 | 誰が | やること |
|---|---|---|
| 平日(月〜金) | Claude Code(`.claude/agents/`のパイプライン) | キーワード調査→一次情報収集→下書き執筆→編集チェックまでを実行し、microCMSに「下書き」で保存 |
| 平日(月〜金) | 人間 | チャットで届く日次ダイジェストを読み、OK/差し戻し/修正指示を20分以内で返すだけ |
| 週末(土日) | 人間 | 下書きに残った【要・実体験の記入】を埋める、写真を追加、最終確認して公開。次バッチの企画承認 |

## 平日パイプライン(自動化する部分)

1. `seo-researcher` が承認済みトピックリストから1〜2本を選び、見出し構成案を作る
2. `outdoor-researcher` がスペック・製品情報を一次情報ベースで調べる(実体験は書かない)
3. `writer` が下書きを執筆する。実体験が必要な箇所は本文に明示的なプレースホルダーを残す
4. `editor` がファクトチェック・トーンチェックを行い、公開可否を判定する
5. その日の全下書きをまとめて、次のフォーマットで日次ダイジェストを作成する:

```
【8/25 下書き完成分】
1. タイトル: 秋の登山レイヤリング、何をどう重ねるか
   判定: 要修正(実体験の記入待ち・2箇所)
   確認してほしいこと: ①レイヤリングの具体的な着用感 ②使用したブランド名の実名記載可否
2. タイトル: ...
```

人間はこれを読んで「①②はOK、③だけ直して」のように返信するだけで良い。1件あたり1〜2分、
1日数件でも20分以内に収まる分量に保つ(ダイジェストが長くなりすぎたらeditorに絞り込ませる)。

## 週末の作業

- 下書きに残ったプレースホルダーを実体験・写真で埋める
- 最終的な公開判断(microCMSで公開ステータスに変更)
- 次の1〜2週間分のトピックを`seo-researcher`の提案から選んで承認する
- 記事が増えてきたら、この曜日にUmami/GSCの数値もざっと確認する(`marketing-analyst`)

## 2026年8月の加速スケジュール(今月10本の目標)

前提: microCMSアカウント作成がまだの場合、これが最初のブロッカーになる。8/22-23の週末で
アカウント作成まで終わらせるのが最短ルート。

| 日程 | やること |
|---|---|
| 8/22(土)〜23(日) | microCMSアカウント作成・API接続確認。下記トピックリストを承認(差し替えOK) |
| 8/24(月)〜28(金) | 平日パイプラインで5〜6本を下書き→日次20分チェック |
| 8/29(土)〜30(日) | 実体験・写真を足して公開、残りを仕上げて合計10本を目指す |

平日に生成する下書き本数は、承認された記事の複雑さ(実体験の分量)次第で調整する。
「本数を優先して薄い記事を量産する」より、「10本のうち実体験の説得力があるものを優先して仕上げる」
方針を崩さないこと(オーガニック検索・アフィリエイト両面で薄い記事は評価されない)。

## 本文内で使える共通パーツ(AI生成感を減らすための仕掛け)

「いかにもAIが書いた」記事は上位表示が難しくなっている前提で、以下の3つを標準装備にする。
`writer`エージェントは対象KWの記事にこれらを最低1箇所ずつ入れることを検討し、無理に入れない
(内容に合わないなら省略してよい。仕掛けのための仕掛けにしない)。

### 1. 監修者(構造化フィールド、本文には書かない)

記事APIの `supervisorName` / `supervisorTitle` / `supervisorBio` / `supervisorImage` に入力する
(`docs/microcms-schema.md` 参照)。記事末尾に自動でボックス表示される。監修者を立てない記事は
空欄のままでよい(無理に架空の監修者を作らない)。

### 2. 診断表(本文中、リッチエディタを「HTML編集」モードにして貼る)

選び方・比較・早見表など、意思決定を助ける場面で使う。

```html
<div class="diagnostic-table-wrap">
  <table class="diagnostic-table">
    <caption>身長別 トレッキングポールの長さ早見表</caption>
    <thead>
      <tr><th>身長</th><th>目安の長さ</th><th>備考</th></tr>
    </thead>
    <tbody>
      <tr><td>150〜160cm</td><td>100〜105cm</td><td>平地〜緩い上り基準</td></tr>
      <tr><td>160〜170cm</td><td>105〜115cm</td><td></td></tr>
      <tr><td>170cm〜</td><td>115〜125cm</td><td></td></tr>
    </tbody>
  </table>
</div>
```

### 3. 一次情報・実体験の裏付け(本文中)

編集部が実際に確認・計測・使用した情報だと分かる形で明示する。捏造しない。

```html
<div class="firsthand-note">
  <span class="firsthand-note-label">編集部の一次情報</span>
  <p>実際に使用した個体で計測。〇〇の重量はメーカー公表値と実測値で12g差があった、など。</p>
</div>
```

実体験がまだ無い箇所は、従来通りプレースホルダーとして残す(週末に本人が埋める)。
目立たせたい場合は以下のマークアップも使える。

```html
<p class="todo-placeholder">【要・実体験の記入】実際に使ってみた感想をここに追記</p>
```

## ブロッカーになりやすい点

- microCMSアカウントが無いと下書きの保存先が無い → 最優先で今週末に作成
- 実体験プレースホルダーが埋まらないまま週末が終わると公開できない → 週末に埋める時間を確保する
- アフィリエイトASPの審査(A8.net等)は記事本数・実績を求められる場合がある → 早めに申請しておき、
  承認を待つ間に記事を増やす
