# 記事ごとの設計ドキュメントについて

記事本文はmicroCMSに入るが(`CLAUDE.md`)、**その記事を書く前に決めたこと**
(誰に向けて書くか、SERPのどこを狙うか、なぜこの見出し構成にしたか、内部リンクの計画)は
チャットやローカルのスクラッチファイルに置き去りにせず、**このフォルダにmdで保管する。**

チャットのセッションは引き継がれないため、次にこのキーワードクラスターの記事を書くとき
(または既存記事をリライトするとき)、このフォルダを見れば同じ調査をやり直さずに済む。

## ファイルの置き方

- 1記事につき1ファイル。ファイル名は**記事のスラッグと同じ**にする
  (例: 記事 `salomon-hiking-shoes` → `docs/articles/salomon-hiking-shoes.md`)
- 記事を作る作業ブランチで、本文と同じタイミングでこのファイルもコミットする
- リライトしたら、このファイルも同じPRで更新する(SERPの変化・新しく足した一次情報など)

## 書く内容(テンプレート)

新しい記事の設計ドキュメントを作るときは、次の見出しをベースにする
(全部を毎回びっしり書く必要はない。**次にこの記事を触る人が判断に迷わない量**でよい)。

```markdown
# 「<主対策KW>」記事の設計ドキュメント

## メタ情報
（タイトル・スラッグ・概要・カテゴリ・タグ・reviewItem等）

## ペルソナ
（誰に向けて書いたか。docs/persona.mdのP1をこの記事用にどう具体化したか）

## 検索意図とSERPの状況
（Ahrefs等で調べた月間検索数・関連KW・上位表示の顔ぶれ・空白地帯）

## タイトル設計の根拠
（なぜこのタイトルにしたか。捨てた案とその理由も残す）

## 見出し構成とその根拠
（どのH2がどの検索需要・PAAに対応しているか）

## 内部リンク方針
（今リンクを張った記事／将来リンクを追加すべき記事とその条件）

## 構造化データ
（faq / reviewItem等、何を設定したか）

## 執筆後に分かったこと・次回への申し送り
（公開後に直した表現、リッチリザルトテストで踏んだ落とし穴など。
  一般化できるものは docs/tone-and-manner.md に反映してから、ここには
  「この記事固有の話」だけ残す）
```

## 一般化できる学びは `docs/tone-and-manner.md` へ

「この言い回しは毎回避けるべき」「画像はこう貼る」のような、**どの記事にも当てはまる
ルール**は、このフォルダではなく `docs/tone-and-manner.md` に書く。このフォルダは
あくまで「その記事固有の設計判断」を残す場所。
