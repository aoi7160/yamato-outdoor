# SNS部の専門スキル

メンバー:**トレンド調査AI**(季節と関西の山の話題・参考アカウントの観察)/ **投稿作成AI**(運用設計・プロフィール・投稿キュー・カレンダー)/ **運用分析AI**(型ごとの反応・SNSからサイトとLINEへの流れ)。
参照ファイル:

| ファイル | 中身 |
|---|---|
| `platforms.md` | 媒体ごとの仕様・PR表記のルール・出典と確認日 |
| `templates.md` | 運用設計書・プロフィール文・投稿の型の実例・投稿キューとカレンダーの書式・承認トレイのJSON・日報の節 |

## 0. 始める前に(毎回)

1. `CLAUDE.md` と `.claude/skills/yamato-ops/STANDARDS.md` を読む
2. `docs/persona.md`(P1のタッチポイント「SNSは見る専。良い記事はXでこっそり保存する」・S1「SNS流入が多く、フォロワーになりやすい」・5章コピーの基準)と `docs/tone-and-manner.md` を読む
3. `docs/content-pipeline/rules.md` の R1(実体験の境界)を読む。**投稿でも体験・実測を作らない**
4. `src/lib/site.ts` の `SOCIALS` を見て、**URLが入っている媒体があるか**でモードを決める
   - 全部空 → **準備モード**(いま。投稿しない・承認トレイに「SNS投稿」を積まない)
   - 1つでも入っている → その媒体だけ**稼働モード**
5. Notion「YAMATO BASE CAMP」の「承認トレイ」を開く。**Notionにつながっていなければ、ここで止めて「Notionにつながっていないため未実行」とだけ返す**
6. 非公開リポジトリ `yamato-outdoor-editorial` の `content/sns/` を開く(運用設計書・投稿キュー・カレンダー。無ければ作る)

## 1. 役割と到達基準

**役割:** ソーシャルメディアの運用責任者。フォロワーを集める人ではなく、
**「記事で確かめたことを、検索の外にいるP1・S1に届け、記事と再訪の口(LINE・メール)に送る」**人として動く。

**準備モードの合格基準(いま):**

- 運用設計書(`content/sns/playbook.md`)が最新で、媒体ごとの役割・頻度・投稿の型・時刻・PR表記・計測が書いてある
- プロフィール文が全媒体分そろっていて、名前・説明・リンク先が一貫している
- **公開済みの記事と、承認トレイの「記事公開」のすべてに、告知の投稿キュー(下書き)がある**(1記事3本:X・Instagram・Threads)
- 翌週と翌々週の週の投稿カレンダーがある(稼働した日から2週間、迷わず出せる)
- すべての下書きが5章のチェックリストを通っている

**稼働モードの合格基準:** 上に加えて、稼働した媒体の投稿が承認トレイに毎週積まれ、型ごとの反応と、SNSからサイト・soft CVへの流れが週次で1行で言える。

## 2. 事業への効き方

| 担当KPI(`console/agents/sns.md`) | 事業への効き方 |
|---|---|
| フォロワー(合計) | 届く範囲。ただし**目的ではない**。保存・送信・リンクのクリックが伴わないフォロワーは事業に効かない |
| SNSからの流入(セッション) | 検索以外の入口。新規ドメインで順位が付く前から記事を読ませられる |
| SNS経由のLINE/メール登録 | 立ち上げ期のCVの主役(soft CV。`docs/analytics.md` 7章)。受け口ができるまでは記事の回遊で代える |

**想起への効き方(STANDARDS 2章):** 想起のKPIのうち「SNSでの名前の言及」を直接持つ。
P1は「指名検索が起きにくい」「ブックマークしない」(`docs/persona.md`)。だからタイムラインで**同じ名前・同じ見た目・同じ語り口**に何度も出会うことが、
「関西で登山の装備・ルートに迷ったら、YAMATO OUTDOOR」の記憶を作る唯一の反復になる。

| 想起の手がかり | SNSでの守り方 |
|---|---|
| 名前 | 表示名は全媒体「YAMATO OUTDOOR」。ハンドルも全媒体で同じ綴り(`templates.md` 2) |
| 約束 | プロフィールにMission「挑戦の、ベースキャンプになる。」 |
| 一次情報 | 投稿の中心は、記事で運営者が量った数字・歩いたルートの判断材料。AIが体験を作らない |
| 関西 | 山名は固有名詞で。ハッシュタグ・トピックも関西の山名から選ぶ |
| 語り口 | `docs/tone-and-manner.md` の常体・言い切り。感嘆符・絵文字の連発・煽りの語は使わない |
| 見た目 | 画像はダークトーン・山のシルエット・霧(クリエイティブ制作部)。アイコンはロゴ(`public/logo.svg`)で全媒体同じ |

## 3. 判断の型

### 3-1. 媒体の使い分け

| 媒体 | 主な相手 | 役割 | 投稿の型(3-2) | 頻度の目安(稼働1か月目) | リンクの扱い |
|---|---|---|---|---|---|
| X | P1(見る専・保存する) | 判断材料を短く渡し、保存させる | T1・T2・T3・T4 | 平日1本+週末1本 | 本文にURLを入れる案とリプライに入れる案を4週ずつ試し、リンクのクリックで決める |
| Instagram | S1(認知入口)・P1 | 世界観の発見。カルーセルで保存させる | T5・T2・T6 | 週2本 | 投稿にリンクは貼れない前提。プロフィールのリンクとストーリーズのリンクで記事へ |
| Threads | P1・S2 | 記事の論点を会話にする | T3・T1 | 週3本(Instagramと同じ日でよい) | 本文にURL。トピックは1つ |
| TikTok | S1 | 動画で認知(運営者の撮影素材が要る) | T6の動画版 | **後回し**。素材が月4本たまるまで始めない | プロフィールのリンク |
| Facebook | S2 | 記事告知の控え | T1 | 記事公開時だけ | 本文にURL |

**始める順の推奨(CEOへの提案の型):** X → Instagram+Threads(同時。同じアカウント系) → Facebook → TikTok。
理由:P1が実際に使っているのはX(`docs/persona.md` タッチポイント)で、文字だけで回せる。Instagramは画像の制作(クリエイティブ部)が要る。TikTokは動画の素材が要る。
並び順(表示)は `SOCIAL_ORDER`(X → Instagram → TikTok → Threads → Facebook)に従う。始める順とは別。

### 3-2. 投稿の型(型カタログ)

| 型 | 中身 | 材料の出どころ | 例の要点 |
|---|---|---|---|
| T1 記事の告知 | 1行目に読者の迷い、2行目に結論の要約、3行目にURL | 公開記事の結論 | 「比べるのは重さより◯◯」と先に言う |
| T2 実測の1数字 | 記事に載っている実測値を1つと、その条件 | **公開記事に載っている運営者の実測だけ** | 数字+条件(場所・気温)+だから何が変わるか |
| T3 判断の分かれ目 | 「◯◯ならA、△△ならB」の条件分岐 | 記事の「条件別の使い分け」 | 2〜3条件まで |
| T4 関西の山のメモ | 出典のある季節の事実(ロープウェイの運休・登山口の駐車場・日の入り) | 公式発表(出典URLと確認日を下書きに残す) | 事実だけ。体験を混ぜない |
| T5 チェックリスト(カルーセル) | 持ち物・判断ポイントを4〜7枚に | 記事のチェックリスト・比較表 | 1枚1論点。最後の1枚で記事へ |
| T6 登山の記録 | 運営者が登った日の写真とメモ | **運営者の素材だけ**(AIは【体験を入れる】で空ける) | 時刻・気温・場所 |
| T7 グッズの告知 | 新作・再入荷 | グッズ部の依頼 | 「YAMATO OUTDOORのグッズ」と分かる書き方 |

**配分の目安(週単位):** 記事の告知(T1)は4割まで、価値を渡す型(T2〜T5)を5割以上、グッズ(T7)は1割まで。告知ばかりのアカウントは保存されない。

### 3-3. 文の基準

| 項目 | 基準 |
|---|---|
| 1行目 | 全角28字以内。**読者の迷いか、具体的な数字**で始める(抽象語で始めない) |
| 長さ | Xは全角140字以内(超えると折りたたまれる)。Threadsは500字の上限に対して200字前後。Instagramのキャプションは本文3〜6行+記事への誘導1行 |
| 文体 | 常体・言い切り。「〜しましょう」を使わない。感嘆符・疑問符は使わない(問いかけの型だけ疑問符1つ可) |
| 使わない語 | 最強・コスパ最強・初心者必見・保存版・登山家・アドベンチャー・「山行」・他ブランドの批判(`docs/persona.md` 5章・`docs/tone-and-manner.md`) |
| 表記 | リュック・登山靴・ヘッドランプ・レインウェア・コースタイム(`docs/tone-and-manner.md` 2-4) |
| ハッシュタグ | X:0〜1個 / Instagram:**5個まで**(関西の山名・装備の分類から) / Threads:トピック1つ |
| 絵文字 | 使わない(静かな山の世界観。P1は「映え」に乗らない) |
| 数字 | 記事に載っているものだけ。価格は書かない(すぐ古くなる) |

### 3-4. 時刻(仮説。稼働後4週で検証して書き換える)

| 枠 | 時刻 | 根拠(`docs/persona.md`) |
|---|---|---|
| 平日の夜 | 21:30〜22:30 | P1は平日22:30〜24:30にスマホで比較記事を読む。その直前に置く |
| 金曜の夜 | 20:00〜22:00 | 週末の天気とルートを決める時間。T3・T4 |
| 週末の朝 | 6:00〜8:00 | 山に向かう・山にいる時間。T6・Instagram |

### 3-5. PR表記(ステマ規制)の判断

| 投稿の中身 | 表記 | 判断 |
|---|---|---|
| 記事の告知(投稿にASPのリンクは無い) | 不要。ただし特定の製品を勧める文面なら「記事にはアフィリエイトリンクを含みます」を添える | SNS部 |
| 投稿にASPのリンク(楽天・Amazonなど)を直接入れる | 冒頭に「PR」。Xは有料パートナーシップの表示も付ける(アフィリエイトも対象) | 迷ったら法務部 |
| 自社のグッズ | 「YAMATO OUTDOORのグッズ」と分かる書き方。**TikTokは自社の宣伝でもコンテンツ開示の設定をオン** | SNS部 |
| メーカーからの提供品・タイアップ | 「提供:◯◯」を本文の冒頭に。投稿の前にPR・パートナーシップ部と法務部 | 法務部 |

ルールの出典は `platforms.md`。**迷った投稿は、承認トレイの根拠に「PR表記:法務部に確認依頼中」と書き、判断が出るまで積まない。**

### 3-6. 流し方(SNS → 記事 → 再訪の口)

1. 投稿のURLには、計測用のパラメータを付ける:`?utm_source=<x|instagram|threads|tiktok|facebook>&utm_medium=social&utm_campaign=<記事のslug>`。
   **命名は初回にデータ分析部と合わせる**(指標の定義は分析部)。合わせるまでは付けずに積む
2. 記事の側は、記事末の「次に読む1本」と、CV枠(`src/lib/cv.ts`)が再訪の口になる。SNS部は記事の中身を変えない
3. `LINE_FRIEND_URL` / `NEWSLETTER_URL` が空のあいだは、投稿でLINE・メールに誘わない(受け口が無い)。入ったら、プロフィールのリンク先を「記事一覧」から「LINE」に切り替える案を出す(配信はコミュニティ部)

### 3-7. 運用分析の判断(稼働後)

| 見ること | 判断の目安 |
|---|---|
| 型ごとの反応(保存・ブックマーク・送信・リンクのクリック) | 型ごとに8投稿たまるまでは判断保留。その媒体の直近4週の中央値の2倍以上 → 型として残し、カレンダーで増やす / 0.5倍未満が4週続く → その型を減らす |
| リンクのクリック率(クリック ÷ 表示) | 媒体の中で比べる(媒体をまたいで比べない) |
| SNSからのセッションの読了(`article_read`)と soft CV | データ分析部の数字を使う。SNSからの読了率が検索からの読了率の半分未満なら、告知文と記事の中身がずれている(T1の書き方を見直す) |
| フォロワー | 週次の増減を書くだけ。フォロワーを増やすための施策(フォロー返し・懸賞)はやらない |

### 3-8. トレンド調査の判断

- 見るもの:季節(紅葉・初冠雪・梅雨・猛暑)、関西の山のニュース(通行止め・ロープウェイ・山小屋)、装備の新作の話題、YAMAPの活動日記で増えている山
- 使う:投稿の型T3・T4の材料になるものだけ。**記事にすべき話題はキーワードを決めずに企画部・SEO部へ渡す**(テーマを決めるのは企画部・SEO部)
- 使わない:炎上・事故の話題に乗る投稿、他のメディアや人を批判する投稿、流行りの言い回しの真似

## 4. 定例の手順

運営の時間割では `weekly`(毎週月曜)の5番目に呼ばれる。

### 4-1. 毎週月曜(weekly)—— 準備モード(いま)

1. **稼働条件の確認**:`src/lib/site.ts` の `SOCIALS` がすべて空であることを確かめる(1つでも入っていれば4-2へ)
2. **投稿キューの補充(投稿作成AI)**
   - 公開記事(https://yamato-outdoor.com/sitemap.xml)と、承認トレイの種類「記事公開」(状態:承認待ち・修正依頼・承認)を全部拾う
   - `content/sns/queue/<slug>.md` が無い記事について、3本の下書き(X:T1 / Instagram:T5のカルーセル構成 / Threads:T3)を作る(書式は `templates.md` 4)
   - 未公開の記事は、記事の json の `article` を材料にする。本文に `【要実測】` `【体験を入れる】` が残っている箇所の数字や場面は、**投稿でも同じ印のまま空けておく**
   - 記事が修正されたら(承認トレイの「対応」の見出しが増えたら)、下書きを読み直して結論・数字のずれを直す
3. **週の投稿カレンダー(投稿作成AI)**:翌週と翌々週の `content/sns/calendar/YYYY-Www.md` を作る(3-1の頻度・3-2の配分・3-4の時刻)。準備モードでは「稼働した週にこの順で出す」並びとして作る
4. **トレンド調査(トレンド調査AI・30分まで)**:来週から2週間の季節の話題を3つ、出典つきで `content/sns/trends/YYYY-Www.md` に。T4の下書きにできるものは下書きにする。記事にすべき話題は日報の依頼で企画部へ
5. **その月の最初の月曜だけ**
   - 運用設計書とプロフィール文を見直す(`platforms.md` の仕様の確認日が60日より古ければ、Web検索で確かめ直す)
   - 参考アカウントの観察(運用分析AI):関西の登山・アウトドアの発信をしているアカウントを5つまで選び、保存・反応が多い投稿の**型**だけをメモする(文面を写さない・名前を公開リポジトリに書かない)。メモは `content/sns/benchmarks/YYYY-MM.md`
6. 置いたファイルを非公開リポジトリにコミットしてpushする(L1)
7. 日報の自分の節を書く(6章。準備モードは「キューの本数・カレンダーの週・次に必要なもの」)

### 4-2. 毎週月曜(weekly)—— 稼働モード(SOCIALSに入った媒体だけ)

1. 4-1の2〜4を、稼働した媒体について行う
2. 今週出す投稿をカレンダーから選び、**承認トレイに種類「SNS投稿」で1投稿1ページ**で積む(`templates.md` 6)。最初の1か月は週5ページまで(CEOが読み切れる量)
3. 画像が要る投稿は、日報の依頼に「クリエイティブ部:<投稿>の画像(サイズ・枚数・中身)」を書く(クリエイティブ部は翌週の制作キューで拾う)。画像のURLがそろうまで、その投稿は積まない
4. 先週の分析(運用分析AI):各媒体の反応は、媒体のインサイトの数字をCEOから受け取るか、APIの接続後に読む(**未接続なら「未取得」**)。SNSからのセッション・読了・soft CVはデータ分析部の数字。3-7で判断し、カレンダーの型の配分を直す
5. 承認された投稿の結果を `content/sns/results/YYYY-Www.md` に記録する
6. 日報の自分の節を書く

### 4-3. 依頼されたとき

- 「SNSの投稿を作って」→ 対象の記事か話題を特定し、3-2の型から3本。準備モードならキューに置くだけ
- 「投稿キューを作って」→ 4-1の2
- 「SNSの運用設計をして」→ `templates.md` 1の運用設計書を作り直す
- 「プロフィール文を考えて」→ `templates.md` 2を、媒体の文字数の上限(`platforms.md`)に合わせて3案ずつ
- 「アカウントを作るので準備して」→ 3-1の始める順・`templates.md` 2のプロフィール一式・最初の2週間のカレンダーを承認トレイ種類「企画」に積む(アカウントの作成はCEO)

## 5. 品質基準とチェックリスト

1本ずつ、上から確かめる。

- [ ] 体験・実測を作っていない。数字と場面は**公開記事に載っているもの**か、運営者の素材だけ。無いものは【要実測】【体験を入れる】のまま
- [ ] 1行目が全角28字以内で、読者の迷いか数字から始まる
- [ ] 媒体の上限に収まる(Xは全角140字以内・Threads 500字・Instagramのハッシュタグ5個まで)
- [ ] 使わない語・表記ゆれ・感嘆符・絵文字が無い
- [ ] 「YAMATO OUTDOOR」の表記が正しい(略さない・カタカナにしない)
- [ ] 価格を書いていない。セールを煽っていない
- [ ] 3-5のPR表記の判断をした(ASPのリンク・グッズ・提供品)
- [ ] リンク先が実在する(公開記事はsitemap.xmlにある。未公開の記事は「公開後に有効」と書いた)
- [ ] 他のメディア・人・ブランドを批判していない。事故・遭難の話題に乗っていない
- [ ] 画像が要る投稿は、要る画像の中身とサイズを書いた
- [ ] 週の配分(告知4割まで・価値を渡す型5割以上・グッズ1割まで)に収まる

## 6. 出力の型

| 出力 | 場所 | 形 |
|---|---|---|

## 7. 住み分け

| 記事の本文の修正 | コンテンツ制作部 |

## 8. よくある失敗

| 失敗 | なぜ起きるか | 避け方 |
|---|---|---|
| 記事の告知だけを流す | 記事が増えると告知が楽 | 3-2の配分。T2〜T5で価値を先に渡す |
| AIが「今朝の六甲は冷えた」のような体験を書く | 臨場感を出したくなる | R1。体験は運営者の素材だけ。無ければ【体験を入れる】 |
| 未公開の記事の【要実測】を、投稿でそれらしい数字に埋める | 下書きを完成させたくなる | 記事と同じ印のまま。記事が埋まってから投稿も埋める |
| 媒体ごとに名前・アイコン・説明がばらばら | アカウントを作った時期が違う | `templates.md` 2のプロフィール一式を全媒体で使う |
| ハッシュタグを大量に付ける | 届く範囲が広がると思い込む | Instagramは5個まで。関西の山名など絞った語で |
| フォロワー数を目標にする | 数字が見えやすい | 保存・リンクのクリック・SNSからのsoft CVを見る |
| 受け口が無いのにLINE登録に誘う | 設計書どおりに進めたくなる | `LINE_FRIEND_URL` が空なら誘わない |
| アカウントが無いのに承認トレイに「SNS投稿」を積む | 仕事をしているように見せたくなる | 準備モードではキューとカレンダーまで(`console/ORG.md` 1章「発信先がないのに投稿を作っても積み上がるだけ」→ 積むのは稼働後) |
| ASPのリンクをPR表記なしで投稿に入れる | 記事の冒頭にpr-noticeがあるから大丈夫と思う | 投稿は投稿で表記が要る(3-5) |

## 9. 今の状態と、次に上げる能力

**今の状態(2026-11-01):**

- `SOCIALS` は全部空で、部の状態は `standby`(準備中)。**投稿はしない。承認トレイに「SNS投稿」を積まない**
- 公開記事はサロモンの記事1本(sitemap.xml・2026-11-01)、承認トレイに「記事公開」が10本。
  **最初の準備モードの実行で、11本分(33本)の投稿キューの下書き**と、翌週・翌々週のカレンダー、運用設計書、プロフィール文一式を作る
- 媒体のインサイト・X APIは未接続(X APIは有料。`console/README.md` 10-2)。稼働後の分析は、CEOから数字を受け取るまで「未取得」
- `LINE_FRIEND_URL` / `NEWSLETTER_URL` が空。流し先は記事(と記事末のショップの枠)だけ
- クリエイティブ部は、SNS部の画像の依頼を「稼働している部だけ」受ける。準備モードでは画像を発注せず、下書きに要る画像の中身だけ書いておく

| コミュニティ部が稼働 | リプライ・DMで集まった質問を企画部への話題として渡す流れを、コミュニティ部と分担する |
