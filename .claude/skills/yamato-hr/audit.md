例の数字・件名は**書き方の見本**。2026-11-01時点の実態に触れている箇所は、その日に list_triggers とリポジトリで確かめた内容。

## 1. 名簿の照合手順(週次の棚卸し)

### 1-1. 実体の一覧を作る

| 実体 | どこで見るか | 何を見るか |
|---|---|---|
| 定期実行 | `mcp__Claude_Code_Remote__list_triggers`(必要なら `get_trigger`) | 名前・有効か・cron・next_run_at・last_run(status・fired_at・finished_at)・mcp_connections の name |
| スキル | `.claude/skills/*/SKILL.md` | フロントマターの name・description、「定例の手順」の見出し(### morning など) |
| サブエージェント | `.claude/agents/*.md` | name・description(どのスキルから呼ばれるか) |
| コンソールのサーバー | `console/server/*.js` | 何が・いつ動くか(`connectors.js` は画面を開くたび、`cms.js` は承認のとき、`proofread.js` は1時間ごと など) |
| 時間割 | `.claude/skills/yamato-ops/SKILL.md` | morning / evening / weekly / monthly の表に、どの部がいるか |

**定期実行のプロンプト・ID・接続のIDは、名簿にも日報にも書き写さない。** 名前(「YAMATO 朝の定例(…)」)で呼ぶ。
YAMATO以外の定期実行(名前が「YAMATO」で始まらないもの)は対象外。中身も読み上げない。

### 1-3. メンバーごとの判定

各部の `staff` の1行ずつ、次を順に問う。最初に「はい」になった行の state にする。

1. `console/server/*.js` に、そのメンバーの仕事の処理があり、人の依頼なしに動くか → **auto**(B)
2. そのメンバーの手順を含むスキルを呼ぶ定期実行があり、有効で、要る接続がそろい、直近2回の予定どおりの回で成果物(その部の日報の節・承認トレイのページ・コミット)が出ているか → **auto**(A)
3. そのメンバーの手順が、実在するスキル・サブエージェントに書いてあるか → **on-call**
4. どれでもない → **defined**(配置の案を必ず付ける)

「成果物」の確かめ方:

| 部の仕事 | 成果物 |
|---|---|
| 日報に報告する部(時間割の部すべて) | その日の `YYYY-MM-DD 日報` の「各部の報告」に、その部の見出し3があり、「未実行」以外が書いてある |
| 承認トレイに積む仕事 | 「承認トレイ」に依頼元がその部のidで、その日に作られたページ |
| リポジトリに書く仕事 | `claude/*` ブランチのコミット(非公開リポジトリを含む) |

空振りの目安:開始から終了まで60秒未満で、上の成果物が無い。重い仕事(週次・記事の執筆)なら数分〜数十分かかるのが普通。

## 2. state の細則

| 状況 | 判定 |
|---|---|
| 定期実行あり・接続なし | on-call(手順がスキルにあれば)。名簿の runs に「定期実行は登録済みだが接続が無く動いていない(確認日)」と書いてよい |
| 定期実行あり・接続あり・まだ1回も動いていない | on-call。初回の成果物を見てから判断 |
| 1回だけ成果物が出た | on-call のまま。2回続いたら auto |
| auto だったが、2回続けて空振り・失敗 | on-call に下げる。原因を日報に |
| サーバーで動くが環境変数が未設定で「未接続」と表示される | auto のまま。runs に「環境変数が無ければ未接続と表示」 |
| スキルはあるが、そのメンバーの手順の見出しが無い | defined 扱いで配置の案(スキルの持ち主への依頼)。名簿上は手順が足されるまで on-call にしない |
| 部が `planned`・`standby` で、準備作業(下書き・設計)の手順がスキルにある | on-call(準備作業を does に書く)。配信・投稿そのものはしない |

## 3. 能力の棚卸しの観点(各部のスキル)

段ごとに、合格の例と不合格の例で判断する。

| 段 | 見るところ | 合格 | 不合格 |
|---|---|---|---|
| 1 9見出し | `## ` の見出し | 9つそろう(`roster_audit.mjs` の [9見出し] が0件) | 1つでも欠ける |
| 2 判断の型 | 「判断の型」の章 | 数値の閾値・順番・表があり、YAMATO OUTDOORの現状(新規ドメイン・記事が少ない・関西・P1)に合わせてある | 一般論の羅列。「適切に」「状況に応じて」で終わる |
| 3 定例の手順 | 「定例の手順」の章 | 時間割の枠(### morning など)ごとに番号つきで、道具・見るもの・書く先が書いてある | 枠の手順が無い・「適宜」「必要に応じて」 |
| 4 住み分け | 「住み分け」の章+手順全体 | 「やらないこと・渡す先」があり、手順が4章の表の他部の「修正」を含まない | 他部の作業を自分の手順にしている |
| 5 今の状態 | 「今の状態と、次に上げる能力」 | 制約(未接続・未提携など)を正直に書き、制約下のL1の準備作業がある | 「できたら始める」だけ。接続していないものを「ある」と書いている |

ほかに、どの段でも不合格にするもの:
- 実在しない数字・実績・提携・接続を「ある」と書いている
- 使わない語(最強・保存版・初心者必見 ほか)・「山行」
- 公開リポジトリに書いてはいけないもの(売上の実額・ID・キー・個人情報)

## 4. 重なりチェック表(住み分けの監査)

`console/ORG.md` 3章の「修正」「判断」の担当を、作業の単位に分けたもの。**担当以外の部のスキルが、その作業を自分の手順(「定例の手順」)に持っていたら重なり**。
「渡す先」「依頼」として書いているのは重なりではない。

| 作業 | 担当(だけが手順に持つ) | 調べ方の例(`grep -n` の語) |
|---|---|---|
| 記事の本文を書く・直す | content | 「本文を書く」「本文を直す」「リライトする」 |
| 公開前の審査・差し戻し | editorial | 「差し戻す」「合格・保留」 |
| キーワードを選ぶ(検索需要) | seo | 「キーワードを選ぶ」「検索ボリューム」 |
| 記事の時期・季節の企画・部への発注 | planning | 「発注書」「公開目標日」 |
| 数字を確定させる・指標の定義 | analytics | 「確定値」「集計する」 |
| 優先順位の案・CEOに決めてほしいこと | executive | 「優先3つ」「決めてほしいこと」 |
| 案件の選定・リンクの差し替え案 | affiliate | 「案件を選ぶ」「buy-box」 |
| 法令・規約のルールの解釈・サイト全体の監査 | legal | 「ルールの解釈」「外部送信の公表」 |
| 売上・費用・作業時間の記帳・P&L | reporting | 「記帳」「P&L」 |
| サムネ・図解・alt を作る | creative | 「サムネ」「図解」 |
| サイト・コンソールの実装・mainへのマージの準備 | dev | 「実装」「ビルド」 |
| 名簿・state の判定・ORG.md の更新 | hr | 「staff」「state」 |
| 投稿キュー | sns | 「投稿キュー」 |
| 配信案(LINE・メール) | community | 「配信案」 |
| グッズの企画・登録の依頼 | goods | 「グッズ」「SUZURI」 |
| 連絡先リスト・提案書 | partnership | 「提案書」「連絡先リスト」 |

調べ方:

```bash
cd /home/user/yamato-outdoor   # 実行環境のリポジトリのルート
grep -n "発注書" .claude/skills/yamato-*/SKILL.md     # planning 以外に「自分が発注書を作る」手順が無いか
grep -n "決めてほしいこと" .claude/skills/yamato-*/SKILL.md
```

ヒットした行を読み、**自分の手順として**書いているか(重なり)、**他部に渡す・依頼する**として書いているか(重なりではない)を見分ける。
grep は入口にすぎない。語が違っても同じ作業なら重なり。

重なりを見つけたら、2つの部の該当行・ORG.md 3章の該当行を並べて、経営企画への報告にする(どちらに寄せるかは経営企画が案を出し、CEOが決める)。

## 5. 承認トレイの型(配置の案・接続を付ける依頼)

| プロパティ | 書くこと |
|---|---|
| 件名 | `企画:<何をすると、誰が動くか>`(例:「企画:定期実行4件に接続を付け、時間割の24人を動かす」) |
| 状態 | 承認待ち |
| 依頼元 | `hr` |
| 種類 | 企画 |
| 根拠 | 1行に1つ:list_triggers で見た事実(名前・接続の有無・直近の回の秒数。確認日)/ 名簿の機械チェックの結果 / 動かないと困ること |
| 承認すると | 誰が何をするか(例:「CEOが各定期実行の設定で Notion・Google Drive・Googleカレンダーの接続を付ける。人事部は次の2回の成果物を見て auto に上げる」) |
| 要約 | 何を・なぜ(1〜2文) |

本文の json(1つだけ):

```json
{
  "changes": [
    "YAMATO 朝の定例:Notion・Google_Calendar を付ける",
    "YAMATO 週次:Notion・Google_Drive・Google_Calendar を付ける",
    "承認後:人事部が成果物を2回確認したメンバーから auto に上げる"
  ],
  "diffs": [
    { "where": "console/agents/planning.md の staff(需要カレンダーAI)", "before": "state: on-call", "after": "state: auto(成果物2回の確認後)", "why": "定期実行で毎朝動き、日報の節が2回続けて出たため。名簿が実態どおりになり、CEOが任せられる範囲を判断できる" }
  ],
  "links": [{ "label": "名簿(コンソール)", "href": "/people/" }]
}
```
