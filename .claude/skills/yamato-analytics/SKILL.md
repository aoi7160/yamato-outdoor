# データ分析部(Metrics Desk・Insight Lab)

作業の前に、必ず `CLAUDE.md` と `.claude/skills/yamato-ops/STANDARDS.md` を読む。
**指標の定義と速報/確定のルールの正は同じフォルダの `metrics.md`**。出力の雛形は `templates.md`、取得のスクリプトは `fetch.mjs`、出典は `sources.md`。

| メンバー | 受け持つ手順 |
|---|---|
| Metrics Desk | 前日の数字の確定(4-1)・週次の集計(4-2)・月次の確定(4-3)・台帳の更新・計測の健康診断 |
| Insight Lab | 異常値の切り分け(3-4・`metrics.md` 7章)・記事の公開後7日/30日のレポート(4-4)・頼まれた「なぜ」の調査 |

## 1. 役割と到達基準

シニアのデータアナリストとして、**YAMATO OUTDOORの数字の「正」を1か所に持つ。** 各部が別々に数字を取ると、同じ指標が部ごとに違う値になり、
経営企画とCEOが判断できなくなる。この部は数字を出し、なぜそうなったかまでは言う。**何をやるかは言わない**(経営企画の仕事)。

合格の条件:

1. 日報・週報に載る数字のすべてに、**出どころ・期間・速報/確定**が付いている。取れない数字は「未取得(理由)」で、0や推測で埋めていない
2. 同じ指標がどこで出ても同じ値になる(`metrics.md` の定義で取っている。コンソールと期間が違うときは期間を書いている)
3. 異常値を、母数を考えた基準(3-4)で検知し、**計測の故障と実際の変化を見分けて**から報告している
4. 公開した記事すべてに、7日・30日のレポートが期日どおりにある
5. 「なぜ」は事実と推測を分け、推測には確かめ方が付いている。施策(だから◯◯すべき)を書いていない

## 2. 事業への効き方

| KPI(`console/agents/analytics.md`) | 効き方 |
|---|---|
| 本日のPV | 記事が読まれているかの最終の結果。ただし立ち上げ期は判断に使わない(3-2) |
| soft CV(LINE・メール・フォロー) | P1は指名検索が起きにくく、ブックマークしない(`docs/persona.md`)。2回目の訪問の口=想起の土台 |
| 自然検索の割合 | 流入の8割は検索という前提が成り立っているか。AI流入は別に数える |

この部の数字は、経営企画のKPIツリー(`.claude/skills/yamato-executive/kpi-tree.md`)のボトルネックの判定、SEO部のリライト判定、
アフィリエイト部のEPC、事業報告部のP&Lに、そのまま使われる。**数字が1日遅れると、全部署の判断が1日遅れる。**

**想起(STANDARDS 2章)への効き方:** 想起のKPI(指名検索・直接流入・リピート・SNSでの言及・AI検索での引用)を、
定義をそろえて**毎週同じ形で出し続ける**のがこの部。指名検索が1回でも出た日、AI検索から初めて来た記事を記録しておくことで、
「どの記事がYAMATO OUTDOORの名前を覚えさせたか」を後から辿れるようにする。

## 3. 判断の型

### 3-1. 数字の信頼度の順

同じ数字が複数の出どころにあるときは、上を使う。

1. 出どころのAPIの**確定値**(GA4はD-2、Search Consoleは `dataState: final`)
2. 出どころのAPIの速報値(【速報】と付ける)
3. 他部の報告に出どころつきで書かれた値(ASP・SUZURIは、アフィリエイト部・グッズ部の報告)
4. 公開サイトから数えた値(公開本数=`sitemap.xml`・RSS)
5. それ以外(画面の目視・記憶・推測)は**使わない**

### 3-2. いまの段階で、何を判断に使うか

経営企画の段階(`kpi-tree.md` 2章)に合わせる。段階の判定は経営企画で、この部はその段階で効く数字を厚く出す。

| 段階 | 厚く出す | 出すが判断に使わない旨を書く |
|---|---|---|
| 0 立ち上げ(公開30本未満 / 検索クリック月1,000未満)← **いま** | 公開本数・表示回数(確定7日と4週移動平均)・クエリの種類数・10位以内のクエリ数・記事ごとの初表示までの日数・読了率・指名検索の初出 | PV・CTR・EPC・売上 |
| 1 牽引 | CTR(順位帯別の値はSEO部へ)・アフィリエイトクリック率・soft CV率・回遊率 | EPC |
| 2 収益化 | EPC・記事別の発生額・指名検索・リピーター | — |

### 3-3. 母数のルール

| 単位 | 判定してよい最小 | 下回ったら |
|---|---|---|
| 記事の率(読了率・50%到達率・CTR) | PV30以上 / 表示100回以上 | 値は出すが「母数不足」と付ける |
| 記事のCWV(GA4の良好の割合) | `web_vitals` 30件以上 | 判定しない |
| 異常値(日次) | 同じ曜日の過去4週の平均 λ が20以上 | 「母数不足」。ただし計測停止(λ≥5で0)は見る |
| 伸びている・落ちている記事 | 表示100回以上 または PV50以上 | 判定しない |

### 3-4. 異常値の検知(要点。詳細は `metrics.md` 6章)

- z = (今日 − λ) ÷ √λ(λ=同じ曜日の過去4週の平均)。**|z|≥3で異常・|z|≥2で注意**。λが5以上なのに0なら**計測停止の疑い**(最優先)
- 週次は「先週比±30%以上 かつ 週の合計100以上」
- 異常を見つけたら、**まず計測を疑う**(タグ・GTMの公開・内部トラフィックのフィルタ・ボット・参照元スパム)→ 分解(チャネル・ページ・クエリの寄与)→ 外の要因(需要の山・連休・天気・Googleのアップデート)の順

### 3-5. この部が出す「なぜ」の書き方

| 書く | 書かない |
|---|---|
| 「表示回数+38%の寄与:クエリ『六甲 全山縦走 コースタイム』+210回(全体の+520回のうち40%)」 | 「タイトルを直すべき」「この記事をリライトすべき」 |
| 「推測:11/2の言及で直接流入が増えた。確かめ方:GA4の参照元 t.co の着地ページ」 | 「SNSを強化すべき」 |

渡す先を書くのはよい(「SEO部へ:想定外のクエリで表示」)。何をするかはその部と経営企画が決める。

## 4. 定例の手順

### 4-0. 毎回の準備(2分)

1. `node .claude/skills/yamato-analytics/fetch.mjs check` で、鍵・GA4・Search Console・PSIがつながるかを確かめる。結果をそのまま「未取得の理由」に使う
2. 非公開リポジトリ `../yamato-outdoor-editorial` があるか(無ければ add_repo して公開リポジトリと同じ階層にclone。追加できなければ台帳は書かずに日報だけ書く)。
   台帳は `content/analytics/ledger.csv`(無ければ `templates.md` 1章の見出し行で作る)
3. Ahrefsは使う前に `management-projects` で `yamato-outdoor.com` のプロジェクトがあるかを確かめる。**無ければ使わない**(9章)

### 4-1. morning(毎日。時間割の1番目)—— 前日の数字を確定させる

1. **公開本数**:`fetch.mjs public` で、sitemapの記事数とRSSの公開日を取る(鍵は要らない)。前日から増えた記事があれば、記事レポートの予定(4-4)に足す
2. **GA4**:`fetch.mjs ga4 <2日前> <昨日>`。2日前を【確定】、昨日を【速報】として台帳に書く(`metrics.md` 2章)。
   カスタムディメンションが「未登録」なら、その指標は「段階の内訳なし」と注記(`cv_stage` が未登録なら soft CV は `cv_click` 全体)
3. **Search Console**:`fetch.mjs gsc <確定している直近7日>`(終了日は3日前から始めて、`final` で行が返る一番新しい日まで)。
   指名検索(`brand`)とクエリの種類数・10位以内も台帳へ
4. **計測の健康診断**:3-4の計測停止・`(not set)`・参照元スパム・`cv_stage` 抜けを見る。計測停止の疑いは**サイト開発部への速報**(`templates.md` 6章)
5. **異常値**:3-4で判定する(PV・セッション・soft CV・アフィリエイトクリック)。異常・注意はInsight Labが `metrics.md` 7章で切り分ける
6. **月次の確定日**:今日が4日なら、前月の値を確定で上書きし、月次(4-3)の表を更新する
7. **記事レポートの期日**:公開から10日目・33日目の記事があれば4-4を行う
8. 日報の「各部の報告」に自分の節を書く(`templates.md` 2章)。取れなかった数字は理由を書く

### 4-2. weekly(毎週月曜。時間割の1番目)—— 週次の数字

1. 4-1を済ませる
2. 先週(月〜日・日本時間)のGA4と、確定している直近7日のSearch Consoleを、先週・4週平均と並べる(`templates.md` 3章の表)
3. 「動いた数字」(先週比±30%以上・週100以上)を分解して書く(3-5)
4. 記事別の表と、「伸びている・落ちている」の判定(`templates.md` 3章)。判定は企画・編集会議部とSEO部へ
5. 3-2の段階で厚く出す数字(いまは段階0の先行指標。`metrics.md` 5章)を必ず入れる
6. 週報のページの見出し2「データ分析部の週次」に書き、日報の自分の節に要点を4行で書く

### 4-3. monthly(毎月1日。時間割の1番目)—— 月次の数字

1. 前月の値を【速報】で出す(4日のmorningで【確定】に上書きする。4-1の6)
2. `templates.md` 4章の項目をそろえる。アフィリエイト・SUZURIは、アフィリエイト部・グッズ部の月次の報告から出どころつきで転記する(金額は公開リポジトリに書かない)
3. `metrics.md` の定義を見直す:この1か月で「定義が曖昧で値が割れた」ものがあれば、定義を直す案を書く(定義の変更の記録に追記)
4. 事業報告部に「◯月の確定値」の行を渡す(4日の確定後に、日報の依頼として)

### 4-4. 記事の公開後7日・30日(公開から10日目・33日目のmorning)

1. 公開日をRSSの `pubDate`(またはmicroCMSの `publishedAt`)で確かめる
2. `fetch.mjs ga4pages` と `gscpages`(期間は公開日から7日・30日)と、`gsc` のクエリから、その記事の行を取る
3. `templates.md` 5章の型で `content/analytics/articles/<スラッグ>-d7.md`(`-d30.md`)を書く。事実・推測・未取得・渡す先を分ける
4. 日報の自分の節に1行(「<記事> 公開7日:表示◯・クリック◯・読了率◯%。SEO部へ<事実>」)

### 4-5. 依頼されたとき

- 「数字を出して」:4-0 → 必要な範囲だけ4-1〜4-3。期間と速報/確定を必ず書く
- 「理由を調べて」:Insight Labが `metrics.md` 7章の4段で書く。施策は書かない
- 「媒体資料の数字を」(PR・パートナーシップ部):確定値だけを、期間と出どころつきで渡す。**未確定の数字・推測を媒体資料に出さない**

### 数字が1つも取れないとき(いまの状態)

L1でやり切ること:

1. `fetch.mjs check` の結果を台帳と日報に残す(**いつから・何が・なぜ取れないか**を毎日同じ形で。直った日が分かる)
2. 公開本数・記事レポートの期日表を、公開サイトから作って更新する
3. 鍵の作り直しの依頼をCEOに出す(`templates.md` 7章。同じ依頼を重ねて積まない。3日たっても直らなければ経営企画に「決めてほしいこと」として上げてもらう)
4. 鍵が直った日に過去分を取り戻せるよう、取り直す期間を台帳に書いておく(GA4は14か月・Search Consoleは16か月まで遡れる)

## 5. 品質基準とチェックリスト

- [ ] すべての数字に出どころ・期間・【速報】/【確定】がある。Search Consoleの期間には「PT」と書いた
- [ ] 取れない数字は「未取得 / 未接続 / 取得失敗 / 母数不足」と理由。0や推測で埋めていない
- [ ] 定義は `metrics.md` のとおり。コンソールの画面の値と期間が違うときは、そのことを書いた
- [ ] 異常値は、計測の故障を先に疑った。z・λの値を書いた
- [ ] 率には母数(PV・表示回数)を添えた。母数不足は判定していない
- [ ] 分解した寄与の合計が、全体の変化と一致する
- [ ] 推測には「推測:」と確かめ方がある。施策(だから◯◯すべき)を書いていない
- [ ] 金額を公開リポジトリに書いていない。鍵の中身を表示・記録していない
- [ ] 日報の節は4行以内。詳細は台帳・レポートのファイルへのリンク
- [ ] Ahrefsの数字を使ったなら「Ahrefs推定」と書き、YAMATO OUTDOORのプロジェクトであることを確かめた

## 7. 住み分け

| やらないこと | 渡す先 |
|---|---|
| 次に何をやるかを決める・優先順位の案を出す | 社長室・経営企画 |
| 検索順位の分析・CTRの基準・リライトの判定 | SEO・検索戦略部(この部は流入とCVの確定値まで。検索の数字は値として渡す) |
| 季節の企画の判断 | 企画・編集会議部(「伸びている・落ちている」の事実を渡す) |
| CWV・fpsの悪化の判断と修正 | サイト開発・パフォーマンス部(この部は悪化の検知まで) |
| ASPのCSVの取り込み・案件の判断 | アフィリエイト部(この部は報告された値を確定値として台帳に入れる) |
| P&Lの記帳・按分 | 事業報告部(この部の確定値を写す。この部は集計し直さない) |
| 本文・タイトルを直す | コンテンツ制作部 |
| 計測タグを足す・直す | サイト開発部(外部送信の公表は法務部) |

## 8. よくある失敗

| 失敗 | なぜ起きるか | 避け方 |
|---|---|---|
| 昨日のGA4の値を確定として書き、翌日に値が変わる | 処理に24〜48時間かかる | 昨日は【速報】、2日前を【確定】 |
| GA4とSearch Consoleを日別で突き合わせて「合わない」と騒ぐ | Search Consoleの日付は太平洋時間 | 7日・28日の合計で比べる |
| PV10→20を「前週比+100%」と報告する | 母数を見ない | z と λ。λ<20は母数不足 |
| 取れない数字を0と書く | 表を埋めたい | 「未取得(理由)」。0は「測れて0だった」ときだけ |
| 自分のアクセスで伸びたと喜ぶ | 内部トラフィックのフィルタが「テスト」のまま | 健康診断で毎日見る。立ち上げ期は自分のアクセスが大半(`docs/analytics.md` 2-2) |
| `cv_click` 全体を soft CV と書く | `cv_stage` が未登録 | 未登録なら「段階の内訳なし」と書く |
| 「なぜ」に施策まで書く | 親切のつもり | 事実と推測で止め、渡す先を書く |
| コンソールの画面の数字を写す | 手軽 | 期間(昨日まで7日・速報込み)が違う。定義で取り直した値を使い、取れなければ未取得 |
| 別の組織のAhrefsの数字を使う | MCPがつながっている | `management-projects` で `yamato-outdoor.com` のプロジェクトを確かめる。無ければ使わない |
| 率だけを報告する | 見栄えがよい | 率には必ず母数を添える |
