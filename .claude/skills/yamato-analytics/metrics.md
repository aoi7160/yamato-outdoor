# データ分析部 —— 指標の定義と確定のルール

**ここがYAMATO OUTDOORの数字の定義の正**(`console/ORG.md` 3章「売上・PV・CVの数字」の判断=分析)。
他部・コンソール・日報で同じ名前の数字が違う値になったら、ここの定義で取り直した値が正しい。
定義を変えるときは、変えた日と理由をこのファイルの最後に書き、変える前と後の両方で1回出す(つながらない数字を並べない)。

---

## 1. 日付と時刻

| 対象 | 1日の区切り | 注意 |
|---|---|---|
| GA4 | **日本時間**(プロパティのタイムゾーンを日本にしている。`docs/analytics.md` 2-1) | 前日のデータは処理に24〜48時間かかり、その間に変わる |
| Search Console | **太平洋時間**(米国カリフォルニア) | 日本時間の日付と一部ずれる。**GA4と日別で突き合わせない。7日・28日の合計で比べる** |
| Clarity | APIは「呼んだ時点から24/48/72時間」 | 日付で区切れない。1日1回、同じ時刻に取る |
| ASP | ASPごと(多くは日本時間) | 発生日と確定日が別 |
| 週 | 月曜〜日曜(日本時間) | Search Consoleは確定している直近の7日を使い、期間を必ず書く |
| 月 | 1日〜末日(日本時間) | 月次の確定は4日(2章) |

## 2. 速報と確定

数字には必ず `【速報】` か `【確定】` を付ける。**確定を書いたあとで値を変えるのは、出どころが値を直したときだけ**(4章の訂正)。

| 出どころ | 速報 | 確定 | 根拠 |
|---|---|---|---|
| GA4 | 前日(D-1) | **2日前(D-2)** | 日次の処理に24〜48時間(`sources.md`) |
| Search Console | `dataState: all` の値(直近2〜3日) | **`dataState: final`**(おおむね3日前まで) | APIの `final` は確定したデータだけを返す |
| Clarity | 取った値がそのまま(過去は取り直せない) | 取った値=確定。取り忘れた日は「未取得」で埋めない | APIは直近1〜3日しか取れない・1日10回まで |
| Bing Webmaster | 直近7日 | 取った週の値 | — |
| PageSpeed Insights / CrUX | — | 取った日の28日移動平均 | 毎日更新 |
| ASP | 発生 | 確定(ASPの承認後。1〜3か月かかる) | 事業報告部のP&Lは確定ベース |
| SUZURI | 注文 | 振込の確定 | グッズ部の報告 |
| 月次 | 1日(monthly)に前月の速報 | **4日のmorningで前月を確定に上書き** | GA4はD-2、Search Consoleは約3日で確定するため |

## 3. 指標の定義

### 3-1. サイト(GA4。内部トラフィックを除いたあとの値)

| 指標 | 定義 | GA4での取り方 | 注意 |
|---|---|---|---|
| PV | ページビュー数 | 指標 `screenPageViews` | `/preview/*` は計測タグなしなので含まれない |
| セッション | セッション数 | `sessions` | 計測タグを遅らせているので、1秒以内の離脱は数えない(少なめに出る。`docs/analytics.md` 1章) |
| ユーザー | アクティブユーザー | `activeUsers` | |
| 自然検索の割合 | 自然検索のセッション ÷ セッション | `sessionDefaultChannelGroup = Organic Search` | AI検索はGA4の既定では Referral に入る。AIは下の「AI流入」で別に数える |
| AI流入 | `traffic_source_kind = ai` のページビュー | カスタムディメンション(イベント) `traffic_source_kind` | 判定リストは `src/components/Analytics.astro` の `AI_HOSTS` |
| 直接流入 | `Direct` のセッション | `sessionDefaultChannelGroup = Direct` | 内部トラフィックのフィルタが「有効」か確かめてから使う(立ち上げ期は自分のアクセスが大半) |
| リピーター | 期間内に戻ってきたユーザー | `newVsReturning = returning` の `activeUsers` | 週次はぶれるので月次で見る |
| 読了率 | 記事の `article_read` ÷ 記事のPV | `article_read`(90%到達)と `page_type = article` のPV | KPIにしない(`docs/analytics.md` 2-5)。記事の質の代理 |
| 50%到達率 | `scroll_depth`(`percent_scrolled = 50`)÷ 記事のPV | | 25%で落ちるなら導入が長い(`docs/analytics.md` 11章) |
| 回遊率 | (`related_click` + 本文の内部リンクのクリック)÷ 記事のPV | いまは `related_click` だけ(本文の内部リンクのクリックは送っていない) | 本文の内部リンクを数えるなら、サイト開発部にイベントの追加を依頼 |
| 目次の利用率 | `toc_click` ÷ 記事のPV | | P1は目次から拾い読みする(`docs/persona.md`) |
| soft CV | `cv_click` のうち `cv_stage = soft` | カスタムディメンション `cv_stage` | 未登録のあいだは `cv_click` 全体を数え、「段階の内訳なし」と注記(コンソールと同じ) |
| hard CV | `cv_click` のうち `cv_stage = hard` | 同上 | `shop`(SUZURIへの遷移)を含む |
| soft CV率 | soft CV ÷ 記事のセッション | | 受け口(`src/lib/site.ts` の `NEWSLETTER_URL` `LINE_FRIEND_URL`)が空なら「受け口なし」と書き、0%と書かない |
| アフィリエイトクリック | `click_outbound` のうち `affiliate_network ≠ none` | カスタムディメンション `affiliate_network` | 発生額はASPで見る。EPC = 発生額 ÷ これ |
| 404 | `page_not_found` の件数と `missing_path` | | 旧URLの転送漏れの検知(サイト開発部へ) |
| CWV(GA4) | 各指標の「良好」の割合(`lcp_rating` などが `good` のイベント ÷ `web_vitals` の件数) | カスタムディメンション `lcp_rating` `inp_rating` `cls_rating` | **良好の割合が75%以上 ⇔ p75が良好。** GA4の標準のレポートではパーセンタイルを出せないため、この形で見る。ページ単位は標本30以上だけ。**INPは操作が無かったページビューも `inp_ms = 0`・`good` で送られる**(`AnalyticsEvents.astro`)ので、良好の割合は高めに出る。INPの判定はCrUXを優先する |

### 3-2. 検索(Search Console。検索タイプ「ウェブ」)

| 指標 | 定義 | 注意 |
|---|---|---|
| 検索クリック(7日) | 確定している直近7日のクリックの合計 | コンソールは「昨日まで7日・速報込み」なので値が違う。日報には期間を書く |
| 表示回数 | 同じ期間の表示回数 | 匿名化されたクエリ・上位以外の行は表に出ないが、合計には入る |
| CTR | クリック ÷ 表示回数 | 掲載順位ごとのCTRの基準はSEO部が持つ(分析部は値を出すだけ) |
| 平均掲載順位 | 表示ごとの最上位の順位の平均 | 順位の分析はSEO部 |
| クエリの種類数 | 表示が1回以上あったクエリの数 | 新規ドメインの先行指標(5章) |
| 10位以内のクエリ数 | 平均掲載順位10位以内のクエリの数 | コンソールの「10位以内」と同じ定義 |
| 指名検索 | クエリに `yamato outdoor`(空白なしも)・`ヤマトアウトドア`・`やまとあうとどあ` を含む表示とクリック | 想起のKPI(STANDARDS 2章)。正規表現は `fetch.mjs` の `brand` |

### 3-3. ほかの出どころ

| 指標 | 定義 | 出どころ |
|---|---|---|
| 公開・更新本数 | 期間内に公開(`publishedAt`)・更新(`revisedAt`)された記事 | microCMS(コンソール)。取れないときは `sitemap.xml` の `lastmod` とRSSの `pubDate`(`fetch.mjs public`)で数え、出どころにそう書く |
| Clarityの行動 | セッション・デッドクリック・レイジクリック・スクロールの深さ | Clarity Data Export API(コンソール) |
| Bing | クリック・表示回数(7日) | Bing Webmaster Tools(コンソール) |
| CrUX | LCP・INP・CLSのp75(28日)。ページかオリジンか | PageSpeed Insights API |
| アフィリエイトの発生・確定 | ASPごとの件数と金額。発生・確定・取消を分ける | アフィリエイト部の報告(ASPのCSVはコンソールのブラウザ内だけにあり、AIは読めない) |
| SUZURIの売上 | 注文数・トリブン | グッズ部の報告 |

**金額(売上・報酬)は公開リポジトリに書かない。** Notionの日報と非公開リポジトリにだけ書く。

## 4. 未取得・訂正の書き方

- 取れない数字は、値の代わりに理由を書く:`未取得(GA4:サービスアカウントの鍵が無効。11/1確認)` / `未接続(Clarity:このセッションにトークンが無い)` /
  `取得失敗(Search Console:403 権限なし)` / `母数不足(表示20回未満)`。**0と書かない。** 推測の値で埋めない
- 確定値を直すとき:`訂正:11/3のPV 1,240 → 1,198(GA4の処理の遅れ。11/5取り直し)` と、日報と台帳の両方に書く

## 5. 新規ドメインの立ち上げ期に見る先行指標

公開記事30本未満・検索クリック月1,000未満のあいだ(経営企画の `kpi-tree.md` の段階0)は、PVの増減は判断に使えない
(母数が小さく、自分のアクセスと季節でぶれる)。代わりに次を毎週出す。

| 先行指標 | 見方 | 渡す先 |
|---|---|---|
| 表示回数(確定7日)とその4週移動平均 | 伸びているか。段階0では「出始めたか」 | 経営企画・SEO部 |
| クエリの種類数・10位以内のクエリ数 | ロングテールが増えているか | SEO部 |
| 記事ごとの初めての表示までの日数 | 公開からの日数。14日を超えて表示0なら、SEO部がインデックスを確かめる | SEO部 |
| 指名検索の初出 | 1回でも出た日を記録する | 経営企画 |
| 読了率・50%到達率(記事別。PV30以上) | 導入と構成が読まれているか | コンテンツ制作部・編集長・校閲部 |
| Clarityのデッドクリック・レイジクリック | 押せない装飾・反応しないUI | サイト開発部 |
| CWVの良好の割合 | 75%を割ったら | サイト開発部 |
| AI流入 | 1件でも出たら記事名と参照元 | SEO部(LLMO) |

## 6. 異常値の検知(前週比の閾値)

数が小さいので「前週比◯%」だけで判定しない。**同じ曜日の過去4週の平均**(λ)と比べ、標準化した差 z = (今日 − λ) ÷ √λ を使う。

| 判定 | 条件 | やること |
|---|---|---|
| 計測停止の疑い | λが5以上なのに今日が0(PV・セッション・`cv_click` のどれか) | **最優先。** サイト開発部に速報(タグ・GTMの公開・環境変数) |
| 異常 | λが20以上 かつ \|z\| が3以上 | 日報に「異常」として理由の切り分け(7章の手順)を書く |
| 注意 | λが20以上 かつ \|z\| が2以上 | 日報に1行。2日続いたら異常と同じ扱い |
| 母数不足 | λが20未満 | 判定しない。「母数不足」と書く |
| 週次の動き | 先週比 ±30%以上 **かつ** 週の合計が100以上 | 週次の「動いた数字」に入れる |

計測の健康診断(毎日):`(not set)` のページが5%超・1つの参照元がセッションの30%超(スパムの疑い)・内部トラフィックのフィルタの状態・
`cv_click` に `cv_stage` が付いていない件数。

例:月曜のPVの過去4週の平均が36、今日が62 → z = (62 − 36) ÷ 6 = 4.3 → 異常。参照元を見る(SNSで言及された・スパム・自分のアクセス)。

## 7. 「なぜ」の出し方(分析AI。次の一手は書かない)

1. **計測を疑う**:タグの変更(`git log --since=… -- src/components/Analytics.astro src/components/AnalyticsEvents.astro src/lib/analytics.ts`)、
   GTMの公開、内部トラフィックのフィルタ、ボット
2. **分解する**:PV = Σ(チャネル別のセッション × セッションあたりのPV)。検索クリック = 表示回数 × CTR。表示回数はクエリ・ページに分ける。
   変化を要素ごとの寄与に分け、**寄与の合計が全体の変化と一致する**ことを確かめる
3. **外の要因を当てる**:需要の山(企画部の需要カレンダー)・連休・天気(雨の週末は登山の検索が減る)・Googleのアップデート(SEO部に確認)
4. **書く**:事実(数字と出どころ)/ 推測(「推測:」と付け、何を見れば確かめられるか)を分ける。**「だから◯◯すべき」は書かない**(経営企画)
