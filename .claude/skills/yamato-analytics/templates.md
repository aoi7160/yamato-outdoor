# データ分析部 —— 出力の雛形

数字の定義は `metrics.md`。ここは「どこに・どの形で書くか」。**値の例はすべて形を示すための例で、実績ではない。**

---

## 1. 台帳(非公開リポジトリ `content/analytics/ledger.csv`)

1行 = 1日 × 1指標。日報・週報・月次はここから作る(同じ数字を2回取らない)。

```csv
date,metric,value,state,source,range,fetched_at,note
2026-11-03,pv,,未取得,GA4,2026-11-03,2026-11-04T06:45+09:00,サービスアカウントの鍵が無効(invalid_grant)
2026-11-03,articles_published_total,1,確定,sitemap.xml,2026-11-03,2026-11-04T06:45+09:00,microCMSに接続できないため公開サイトから数えた
2026-10-31,gsc_clicks_7d,,未取得,Search Console,2026-10-25〜2026-10-31(PT),2026-11-04T06:45+09:00,同上
```

- `state` は `速報` / `確定` / `未取得` / `未接続` / `取得失敗` / `母数不足` / `訂正`
- 金額(アフィリエイト・SUZURI)もここに書いてよい(非公開リポジトリ)。**公開リポジトリには書かない**

## 2. 日報の自分の節(Notion「日報・週報」のその日のページ。4行まで)

### 取れる日

```
### データ分析部
- 結果:【確定 11/2】PV 412・セッション 301(自然検索 58%・AI 3件)・soft CV 2。【確定 10/27〜11/2(PT)】検索クリック 96・表示 4,120・10位以内のクエリ 18
- 判断:PVは月曜の過去4週平均(λ=280)に対し z=+7.9 で異常。参照元の内訳ではX(t.co)が128セッション。計測停止・スパムの兆候なし
- やったこと:台帳を更新。公開7日の記事レポート1本(winter-gloves-hira)を非公開リポジトリに置いた
- 依頼:経営企画 → Xの言及の元の投稿の確認(分析部は数字まで)/ SEO部 → winter-gloves-hira の表示が公開7日で312回、想定KWで表示あり
```

### 取れない日(いま)

```
### データ分析部
- 結果:公開記事 1本(sitemap.xml・11/4 6:45)。PV・soft CV・検索クリックは未取得(GA4・Search Console:サービスアカウントの鍵が無効 invalid_grant。11/1から)
- 判断:鍵が直るまで、確定値を出せるのは公開本数だけ。コンソールの画面の数字はAccessの内側にあり、このセッションからは読めない
- やったこと:台帳に未取得の理由を記録。記事レポートの予定(サロモン:公開30日は済、次は90日)を更新
- 依頼:CEO → 新しい鍵の作成と登録(承認トレイ「データ分析:鍵の作り直しのお願い」に手順)
```

日報のプロパティ(PV・soft CV・検索クリック(7日)・公開・更新)は経営企画が転記する。**分析部の節に無い数字は転記されない**ので、
取れた数字は必ずこの節に書く。

またはPVが同じ条件で50以上。渡す先は企画・編集会議部とSEO部(何をするかは書かない)。

## 4. 月次(1日に速報、4日に確定で上書き。週報と同じページ群の「月次」)

週次の表を月単位にし、次を足す:

- 前月比と、3か月の推移(データ保持は14か月。`docs/analytics.md` 2-2)
- 記事別の月間の表(全記事。PV・表示・クリック・読了率・soft CV・アフィリエイトクリック)
- アフィリエイト:ASP別の発生・確定・取消(アフィリエイト部の報告から。**金額は公開リポジトリに書かない**)、EPC(発生額 ÷ アフィリエイトクリック)
- SUZURI:注文数・トリブン(グッズ部の報告から)
- 想起の4行(指名検索・直接流入・リピーター・soft CV)
- 計測の健康診断の結果と、定義の変更(`metrics.md` 8章)
- 事業報告部へ:「◯月の確定値」として、PV・soft CV・売上(アフィリエイト確定・SUZURI)の行を渡す

## 5. 記事の公開後7日・30日のレポート(非公開リポジトリ `content/analytics/articles/<スラッグ>-d7.md` / `-d30.md`)

公開日(RSSの `pubDate` かmicroCMSの `publishedAt`)から、**7日レポートは10日目、30日レポートは33日目のmorningに作る**
(Search Consoleの確定を待つため)。

```markdown
# <記事タイトル> 公開後7日(公開 2026-11-03 → 集計 11/3〜11/9 JST / GSC 11/3〜11/9 PT 確定)

- URL:https://yamato-outdoor.com/…/
- 主に狙うキーワード:<承認トレイの article.keyword か設計書 docs/articles/<slug>.md>

| 区分 | 指標 | 値 | 状態 |
|---|---|---|---|
| 検索 | 表示 / クリック / CTR / 平均掲載順位 | | |
| 検索 | 表示のあったクエリの数 / うち想定KWを含む | | |
| 検索 | 表示の多いクエリ上位5(表示・順位) | | |
| 行動 | PV / セッション / 平均エンゲージメント時間 | | |
| 行動 | 50%到達率 / 読了率 / 目次の利用率 / 回遊率 | | |
| 成果 | soft CV / hard CV / アフィリエイトクリック | | |
| 体験 | CWVの良好の割合(標本30以上のときだけ)/ Clarityのデッドクリック・レイジクリック | | |

## 同じ時期に公開した記事との比較
(公開から同じ日数で比べる。記事が3本未満なら「比較できる記事なし」)

## 事実
- <数字だけで言えること>

## 推測(確かめ方つき)
- 推測:<…>。確かめ方:<…>

## 未取得
- <指標>:<理由>

## 渡す先
- SEO部:<想定外のクエリで出ている・表示0 など、検索側の事実>
- コンテンツ制作部・編集長・校閲部:<25%で止まる・読了率 など、本文側の事実>
- 企画・編集会議部:<伸びている/落ちている の判定>
```

**次の一手(リライトする・タイトルを変える等)は書かない。** 事実と推測までで止め、渡す先に事実を渡す。

## 6. 異常値の速報(日報の自分の節の先頭に1行)

```
- 速報:【計測停止の疑い】11/5 のPVが0(月曜の4週平均 λ=42)。GTMの公開状態・GTM_ID・ANALYTICS_DISABLED を確認してください → サイト開発部
```

## 7. 鍵が無効なときのCEOへの依頼(日報の「依頼」に1行+手順は承認トレイに種類「企画」で1件。同じ依頼を重ねて積まない)

| プロパティ | 書くこと |
|---|---|
| 件名 | データ分析:GA4・Search Consoleの鍵の作り直しのお願い |
| 根拠 | `fetch.mjs check` の結果:`invalid_grant: Invalid JWT Signature`(確認日時)。鍵が削除・無効化されている / 影響:PV・soft CV・検索クリックが未取得のまま |
| 承認すると | (CEOの作業)`console/SETUP.md` 手順4の3で新しいJSONの鍵を作り、Cloudflareの `GOOGLE_SERVICE_ACCOUNT_JSON` と、Claudeの環境のシークレット `GA4_SA_KEY_B64`(JSONをbase64にしたもの)の**両方**を差し替える。あわせて `GA4_PROPERTY_ID` をClaudeの環境にも入れる → 次のmorningで分析部が `fetch.mjs check` で確認する |
| 要約 | 鍵が無効で、日次・週次の数字が未取得になっている。新しい鍵が要る |
