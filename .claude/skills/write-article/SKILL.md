# 記事を書いて、承認トレイに積む(コンテンツ制作部+SEO・検索戦略部)

CEOの理想の流れ:**AIがテーマを選んで公開直前まで書く → 承認トレイに週2〜4本たまる → CEOが全体をさっと読み、
直してほしい箇所にだけコメント・修正案を付ける(コンソールの記事レビュー画面 `/review/`)→ AIが直す → 承認でmicroCMSに下書き入稿 → CEOが公開。**

このスキルは、その「AIが書く」「AIが直す」の部分。**公開・mainへのマージ・外部への送信はしない。** 積むのはNotionだけ。

## 0. 最初に読むもの(毎回)

1. `CLAUDE.md`(サイトの約束)
2. `docs/persona.md`(誰に向けて書くか。**矛盾したらこれが正**)
3. `docs/tone-and-manner.md`(文体・表記・見出し・公開前チェックリスト)。冒頭の「お手本にする記事」を必ず読む
4. **お手本の記事**:https://yamato-outdoor.com/mountain-climbing/boots/salomon-hiking-shoes/ を取得して本文を読む
   (語り口・段落の長さ・言い切りの強さ・一般論と体験の混ぜ方を、ここに寄せる)。
   **ナイトハイクの記事はお手本にしない**(書き方がCEOの想定と違う)
5. `docs/microcms-schema.md` の「カテゴリ設計」(ピラー P01〜P08 とカテゴリの対応)
6. `docs/articles/README.md` と、既存の設計書 `docs/articles/*.md`

## 1. まず、承認トレイの修正依頼を片付ける(新しく書くより先)

Notion「YAMATO BASE CAMP」→「承認トレイ」(データソースはページ内の「承認トレイ」データベース)で、
**種類が「記事公開」で、状態が「修正依頼」**のページを探す。あれば、それを先に直す。

- ページ本文の最新の見出し3「CEOの判断(日時)修正依頼(…)」の下の箇条書きが指示。
  - `全体:…` … 記事全体への指示
  - `「引用」:コメント:…` … 引用した本文の箇所へのコメント。引用を本文から探して、その意図に沿って直す
  - `「引用」:修正案:「…」に直す(理由:…)` … その箇所を、ほぼその文面に差し替える(前後とつながるように最小限の調整は可)
- 「修正の大きさ」が **大きな修正** なら、構成から書き直してよい(タイトル・h2・想定読者まで見直す)
- 直したら、本文の ```json の `article` を書き換え、見出し3「対応(日時)修正◯回目」に**何をどう直したか**を箇条書きで書き、
  状態を「承認待ち」に戻す
- 指示どおりにできない箇所(事実と違う・ルールに反する)があれば、直さずに「対応」の箇条書きに理由を書く

## 2. テーマ(キーワード)を選ぶ

1回の実行で書くのは **1〜2本**。承認トレイに「記事公開」で「承認待ち」のものが **4本以上あれば、新しくは書かない**
(CEOが読み切れない量を積まない)。

候補の出し方(上から優先):

1. 承認トレイの「企画」で**状態が「承認」**のもの(企画・編集会議部の企画をCEOが承認したもの)。書いたら、その企画ページを「対応済み」にする
2. 需要の山(`console/src/scripts/demo.ts` の `PEAKS`、GoogleカレンダーのYAMATO BASE CAMP)の**6〜8週間前**に公開できるもの
3. サイトマップ(https://yamato-outdoor.com/sitemap.xml)と `docs/microcms-schema.md` のピラーを突き合わせ、
   **まだ記事が無いピラー**、または既存記事から内部リンクでつなげられる隣のテーマ

キーワードは WebSearch で検索結果の上位・関連する質問を見て決める(Ahrefsは使わない)。
すでにある記事・承認トレイにある記事と**同じキーワードを狙わない**(共食いになる)。

## 3. 書く

- 想定読者は `docs/persona.md` のP1を、この記事用に具体化する(「関西で働きながら月1〜2回登る人で、…に迷っている」まで)
- 構成は `docs/tone-and-manner.md` の「4. 記事の型」。結論を前半に。h2は4〜8本。分量はハウツー6,000〜10,000字が目安(削って成立するなら削る)
- タイトル全角30〜35字・概要80〜120字。使わない語(最強・保存版・初心者必見ほか)を使わない
- **体験・実測をでっち上げない。** AIには山に行けないので、実測値・体験の描写が要るところは本文にこう書いて空けておく:
  - `【要実測:山頂の気温と風速。日付と時刻も】`
  - `【体験を入れる:どこで何を脱いだか】`
  - `【要確認:メーカー公式の重量(確認日)】`
  CEOのレビュー画面で色が付き、一覧になる。1記事に5〜10か所程度までに抑え、それ以外は調べて書ける内容で埋める
- 価格・スペック・制度などは**出典と確認日**を書く。確認できない数字は書かない
- 内部リンクは2〜4本、**サイトマップに実在するURLだけ**。アフィリエイトのリンクは入れない(案件の選定はアフィリエイト部。入れる場合は冒頭に `pr-notice`)
- 本文は microCMS の `contentHtml` に入るHTML(`<h2>` `<h3>` `<p>` `<ul>` `<table>`、注意書きは `<div class="note">` など既存記事と同じクラス)。FAQは本文に書かず `faq` に入れる

## 4. 自分で校閲する

書いた本文を、コンソールの自動チェックと同じルールで調べる:

```bash
cd console && node --input-type=module -e "
import { checkArticle, RULE_LIST } from './server/proofread.js';
import { readFileSync } from 'node:fs';
const a = JSON.parse(readFileSync(process.argv[1], 'utf8'));
const r = checkArticle({ id: 'draft', ...a, contentHtml: a.html });
for (const c of r.checks) if (!c.ok) console.log(RULE_LIST.find((x) => x.key === c.key).label, c.findings);
" /path/to/article.json
```

引っかかったものは直す(【要実測】などの印による文の長さは気にしなくてよい)。そのうえで `docs/tone-and-manner.md` の
「10. 公開前チェックリスト」を上から見る。

## 5. 承認トレイに積む

Notion「承認トレイ」データベースに1記事1ページ:

| プロパティ | 書くこと |
|---|---|
| 件名 | `新しい記事:<タイトル>` |
| 状態 | 承認待ち |
| 依頼元 | `content` |
| 種類 | 記事公開 |
| 根拠 | 1行に1つ。狙うキーワードと検索結果の様子 / どの需要の山の何週間前か / 既存記事とのつながり / 【要実測】などの数 |
| 承認すると | microCMSに下書きとして入稿 → microCMSの画面で【要実測】を埋めて公開 |
| 要約 | 何の記事で、読者が何を決められるようになるか(1〜2文) |

本文には ```json のコードブロックを**1つだけ**置く(書き方は `console/README.md` 11-1):

```json
{
  "article": {
    "title": "…", "slug": "english-slug", "description": "…", "category": "wear", "tags": ["…"],
    "html": "<p>…</p><h2>…</h2>…", "faq": [{ "question": "…", "answer": "…" }],
    "keyword": "主に狙うキーワード", "reader": "この記事の想定読者", "why": "このテーマ・キーワードにした理由(需要・空白・内部リンク)"
  },
  "links": [{ "label": "つながる既存記事", "href": "https://yamato-outdoor.com/…/" }]
}
```

その下に見出し3「対応(日時)初回」と、設計の要点(検索結果の上位の傾向・捨てた案・見出しの根拠)を箇条書きで残す
(承認されたら、これを `docs/articles/<slug>.md` の設計書にする)。

## 6. 最後に

何をしたか(直した記事・新しく積んだ記事の件名と、【要実測】の数)を短く報告して終わる。
コードの変更・コミット・pushはしない(このスキルが触るのはNotionだけ)。
