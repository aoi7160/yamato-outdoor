# BASE CAMP の記録の置き場(D1)

2026-11-27 から、承認トレイ・日報・週報・台帳は **Notion ではなく D1(Cloudflare のデータベース)** に置く。
Notion の無料枠のブロック上限で、11/18 から日報が書けなくなったため。Notion の「YAMATO BASE CAMP」は読むだけの過去の控え(新しく書かない)。

D1 は、運営者の個人用の Worker「Human OS」が持っている。記録は「種類(kind)」ごとに1件1行の JSON で、項目名は Notion のころと同じ日本語。
管理コンソール(BASE CAMP)の承認トレイ `/review/` も、この D1 を読む(`console/server/tray.js`)。

## 1. 種類

| もとの Notion | 種類(kind) | 1件の単位 | id |
|---|---|---|---|
| 承認トレイ | `yamato_tray` | 1依頼 | 付けなくてよい(自動で8文字)。Notion から移した分は Notion のページid(32文字) |
| 日報・週報 | `yamato_log` | 1日・1週・1か月 | `YYYY-MM-DD-日報` / `YYYY-MM-DD-週報`(その週の月曜) / `YYYY-MM-月次` |
| 案件台帳 | `yamato_deals` | 1案件 | 自動 |
| P&L台帳 | `yamato_pl` | 1取引 | 自動 |
| 作業時間ログ | `yamato_hours` | 1日×1区分 | 自動 |
| 登山記録 | `yamato_climbs` | 1回の登山 | 自動 |
| 月次の締め | `yamato_close` | 1か月 | `YYYY-MM` |
| 連携先のメモ(ファイルID・URLなど公開リポジトリに書かないもの) | `yamato_memo` | 1項目 | 短い英字(例 `content-map`) |

**記録の中身(実額・ID・個人情報)は D1 にだけ置き、公開リポジトリには書かない**(STANDARDS 5章)。

## 2. 読み書きのしかた

どちらかで読み書きする(同じ D1)。

- **Claude アプリ・コネクタ「Human OS」があるとき**:道具 `life_list`(読む)・`life_save`(足す・直す)に、`kind` を上の種類で渡す
- **定期実行(Claude Code)**:Human OS の記録API。URL は定期実行の指示文に書いてある(公開リポジトリには書かない)。認証ヘッダーは `authorization: Bearer proxy-injected` のまま(環境が本物に差し替える)
  - 読む:`curl -s -H "authorization: Bearer proxy-injected" "<URL>/admin/life?kind=yamato_tray&limit=100"`(`&q=語` で絞れる)
  - 書く:`{"kind":"yamato_tray","items":[{…}]}` を一時ファイルに書き、`curl -s -X POST -H "authorization: Bearer proxy-injected" -H "content-type: application/json" --data @<ファイル> <URL>/admin/life`
  - 返ってきた `saved` の id を控える(承認トレイの依頼を日報から指すときに使う)

決まりごと:

- **id がある記録に書くと、送った項目だけ上書きされ、ほかの項目は残る。** 配列(履歴など)は丸ごと置き換わるので、読んでから1件足して全部送る
- **消さない。** 削除はCEOが「消して」と言ったときだけ(定期実行では消さない)
- 書けなかったら(401・5xx・つながらない)、その部の作業はそこで止めて、日報に書けないので最後の報告に「記録(D1)に書けないため未実行:<理由1行>」と書く。**Notion に書きに戻らない**

## 3. 承認トレイ(`yamato_tray`)の1件

| 項目 | 中身 |
|---|---|
| 件名 | CEOが一覧で読む1行 |
| 状態 | `承認待ち`(積むとき)/ `修正依頼` / `承認` / `差し戻し` / `対応済み`。CEOの判断はコンソールが書く |
| 依頼元 | 部のid(`content`・`affiliate` など) |
| 種類 | `記事公開` / `リンク差し替え` / `企画` / `納品` など(各部のスキルの書き方どおり) |
| 根拠 | 1行に1つ(改行区切りの文字列) |
| 承認すると | 承認したら何が起きるか(L2 のときは必ず) |
| 要約 | 3行まで |
| 詳細 | **JSON のオブジェクトのまま**入れる(Notion の本文の ```json の中身にあたる。`console/README.md` 11-1 の形:links・changes・diffs・article・images・preview) |
| 履歴 | `[{ "by": "ceo" か "agent", "title": "CEOの判断(2026-11-27 21:40)修正依頼(…)", "lines": ["…"] }]`。CEOの判断はコンソールが足す。部が対応したら `{"by":"agent","title":"対応(日時)…","lines":[…]}` を末尾に足して、全部送る |
| 修正の指示 / 修正の大きさ / 修正回数 / 判断日時 | コンソールが書く。部は読むだけ |

承認待ちの数え方:`?kind=yamato_tray&limit=200` を読み、`状態` で数える。

## 4. 日報・週報(`yamato_log`)

1つの日報を、部ごとの項目に分けて持つ(同時に書いても消し合わない)。

| 項目 | 中身 |
|---|---|
| タイトル | `2026-11-27 日報` / `2026-11-23 週報` / `2026-11 月次` |
| 日付 / 種類 | `YYYY-MM-DD` / `日報`・`週報`・`月次` |
| 状態 | `未読`(作るとき)/ `既読`(CEOが読んだら) |
| `報告_<部の名前>` | その部の報告(STANDARDS 5章の4行。改行区切りの文字列)。例 `報告_SEO・検索戦略部` |
| 締め | 社長室の締め(本日の合計・明日の優先3つ) |
| 決めてほしいこと | CEOに決めてほしいこと(無ければ書かない) |
| 決定ログ / 発注表 | 週報だけ。配列(決定は「いつ・誰が・何を決めたか・宿題」、発注は「部・内容・期限・状態」) |
| 本文 | 週報・月次の本文(マークダウン) |

その日の朝に最初に動く部が、`{"id":"YYYY-MM-DD-日報","タイトル":"YYYY-MM-DD 日報","日付":"YYYY-MM-DD","種類":"日報","状態":"未読"}` を送って作る(既にあっても同じ内容なので害はない)。
