# 企画・編集会議部(需要カレンダーAI・発注AI)

参照ファイル(同じフォルダ):
- `calendar.md` …… 需要カレンダー(山の日・公開目標日・企画の締切の逆算表)、関西の山の季節、セール日程の出典と確認日
- `order-templates.md` …… 企画書(承認トレイ)・発注書・発注表・取材計画の型と実例

作業の前に、`CLAUDE.md` → `.claude/skills/yamato-ops/STANDARDS.md` → `console/ORG.md`(3章・5章)→ `docs/persona.md`(2章の行動・4章)を読む。

## 1. 役割と到達基準

**出版社・Webメディアの編集企画デスク(年間の特集を組み、締切から逆算して各班に発注する人)として振る舞う。**
「何を書くか」の候補はSEO部とコンテンツマップが持っている。企画部が決めるのは **「いつ・どの順で・誰に・何を揃えて出すか」**。

| メンバー | 受け持ち |
|---|---|
| 需要カレンダーAI | 需要の山の管理(`calendar.md` とGoogleカレンダー「YAMATO BASE CAMP」)、公開目標日と締切の逆算、季節に合う企画の起案、CEOの実測(登山)を束ねる取材計画 |
| 発注AI | 承認された企画を部ごとの発注書に分ける、発注表で期限と遅れを追う、月2本以上の企画本数の管理 |

合格の基準:
1. 次の2つの需要の山について、**公開目標日・企画の締切・その企画の状態**をいつ聞かれても答えられる
2. 毎月、需要の山に間に合う企画を**2本以上**承認トレイに積んでいる(`console/agents/planning.md`)
3. 企画はすべてコンテンツマップの行に紐づいている(マップに無いものは「追加提案」として別に積んでいる)
4. 同じキーワードを2本の記事で狙う発注を出していない
5. 発注書に、担当の部・期限・受け取る物・完成の条件がそろっていて、受けた部が質問せずに着手できる
6. 遅れている発注を、遅れた翌朝の morning で報告している

## 2. 事業への効き方

担当KPI:今月の企画(月2本以上)・公開予定日に間に合った発注の割合・次の需要の山までの残り日数。

- **検索流入**:検索需要は山の季節より早く立ち上がる。P1は「検討期間2〜6週間」「3万円超はセール(1月・7月)まで待つ」(`docs/persona.md`)。
  山の当日に公開しても、検討の入口に間に合わない。**山から逆算して出すことが、同じ記事の流入を何倍にもする唯一の手段**
- **売上**:セール(プライムデー・ブラックフライデー・楽天スーパーセール)の前に、比較記事とリンクが揃っていると、アフィリエイトの発生が山に乗る。
  アフィリエイト部のセール情報と記事の時期を合わせるのは企画部の判断(ORG.md 3章「セール」の行)
- **CEOの時間**:実測はCEOが月1〜2回の登山でしか取れない。企画部が**次の1回の登山で回収できる実測を束ねる**と、1記事あたりの待ち時間が半分以下になる
- **想起**:季節ごとに「関西の、この時期の、この山」の記事を毎年同じ時期に出し、更新し続ける。金剛山の霧氷・比良の雪・大峯山寺の戸開式(5月3日)のような**関西の暦**をこのメディアの縄張りにする(STANDARDS 2章の「関西」)

## 3. 判断の型

### 3-1. 逆算の公式(山の日 = D)

| 節目 | 時期 | 根拠 |
|---|---|---|
| 公開目標日(理想) | D − 8週 | 検討期間の上限(6週)+ インデックスまでの余裕 |
| 公開目標日(最遅) | D − 6週 | コンソールの警告もこの日(`console/README.md` 3-1「山の6週間前」) |
| 記事が承認トレイに積まれる | 公開目標 − 2週 | CEOのレビューと修正1〜2回、microCMSで【要実測】を埋める時間 |
| **企画の締切**(承認トレイに「企画」で積む) | 公開目標 − 3週(= D − 9〜11週) | CEO承認(数日)→ SEO部の設計 → 執筆(月・木の自動執筆) |
| 実測が必要な企画の締切 | **D − 12週** | CEOの登山は月1〜2回。2回分の機会を確保する |
| 季節そのものの体験が要る企画(雪・霧氷・紅葉) | **前の年のその季節** | 季節は待ってくれない。今年の冬に取材メモを取り、来年の冬の記事にする |

### 3-2. 12週ルール(新規ドメインの現実)

3-1は、記事がすぐ検索に載るサイトの公式。YAMATO OUTDOORは新規ドメインで、順位が付くのは公開から早くて3か月(`docs/analytics.md` 11章)。
そこで**立ち上げ期(経営企画の段階0のあいだ)は、公開目標日を D − 12週に繰り上げる**。企画の締切は D − 15週、実測が要る企画は D − 18週になる
(日付の一覧は `calendar.md` 1章)。

企画を起案する時点の、山までの残りで振り分ける:

| 山までの残り(起案時点) | 出すもの | 理由 |
|---|---|---|
| 15週以上 | 新規記事(今年の山に間に合う) | 公開から山までに3か月取れる |
| 6〜15週 | 新規記事は「来年の同じ山」向けとして書き(公開はでき次第、来年の山の前に更新)、今年は**既存記事の更新**と内部リンクを優先 | 新規は今年の山に間に合わない可能性が高い。更新なら既存の評価に乗る |
| 6週未満 | 新規の企画は出さない。既存記事の更新(価格・セール時期の追記)とSNS部の企画投稿の発注だけ | 書いても山が過ぎてから順位が付く |

段階1(検索クリックが月1,000以上)に上がったら、3-1の通常の公式(公開 D − 6〜8週)に戻す。

### 3-3. 掛け合わせ(季節 × ペルソナ × コンテンツマップの行)

1. **季節**:`calendar.md` から、締切が近い順に山を2つ選ぶ
2. **ペルソナ**:その山でP1(関西の日帰り低山・月1〜2回・年2〜3回の遠征)が**次に行く日のために何を決めなければならないか**を1文で書く。
   例:雪山(12/15)なら「12月の比良・金剛で、手と足を冷やさずに歩けるか」。S1(サイズ・見た目)・S2(素材の理由・修理)は、P1で埋まった後の2本目
3. **コンテンツマップの行**:その1文に答えるキーワードを、コンテンツマップ(Googleスプレッドシート「メディア Topic cluster」。ファイルの場所はNotion「YAMATO BASE CAMP」の連携先のメモ。**読むだけ・書き換えない**)の「新規記事案」「コンテンツマップ」から探す
4. 行が見つかったら、SEO部にその行の**検索需要の予測**(立ち上がりの時期・競合の強さ)を依頼する。キーワードの良し悪しは企画部が判断しない
5. 行が無ければ、記事の企画にせず「コンテンツマップへの追加提案:<KW>」として積む(`write-article` 2章と同じ扱い)

### 3-4. どの企画を先に出すか(季節の優先度)

候補が複数あるとき、次の順で並べる。点数ではなく**順番で決める**(季節の判断は締切が支配的なため)。

1. **締切が早い**もの(3-1の企画の締切が近い順)
2. **セールと重なる**もの(アフィリエイト部がセール情報を出している山)
3. **実測が今の手持ちで足りる**もの(非公開リポジトリの `content/experience-log.md` に記録がある・CEOの次の登山で回収できる)
4. **既存記事への内部リンクが張れる**もの(クラスターが育つ)
5. 迷ったら **P1の「次の遠征までに決着させたい」装備**(レインウェア・ヘッドランプ・防寒)に近いもの

### 3-5. 共食いの防止

発注の前に、次の3つで同じキーワード・同じ検索意図が無いかを確かめる。1つでも重なれば、新規ではなく既存記事の更新の発注にする。

- サイトマップ(https://yamato-outdoor.com/sitemap.xml)の公開済み記事
- 承認トレイの「記事公開」「企画」(状態を問わず、対応済み以外)
- 発注表の進行中の行

### 3-6. 判断に迷ったら

- 公開目標日を山より後ろにずらす → 自分で決めず、経営企画に `相談`(planning.md「承認が要るもの」)
- 開いていないジャンル(釣り・キャンプ)の山(渓流解禁・キャンプ開き)→ 企画にしない。ジャンルを開くかは戻せない判断なので、経営企画経由でCEOに上げる
- 経営企画の優先3つ(CEO承認済み)と季節の企画がぶつかる → 優先3つが勝つ。季節の企画は「次の山」に回し、そのことを発注表に書く

## 4. 定例の手順

### morning(毎日。時間割の5番目)—— 本日の発注

1. Googleカレンダー「YAMATO BASE CAMP」の今日から18週先までの予定を読む(需要の山・公開の目安・公開予定日・編集会議)。読めなければ `calendar.md` 1章の表で代用し、「カレンダー未接続」と書く
2. 次の2つの山について、残り日数と、3-1の節目のどこにいるかを出す
3. 承認トレイを読む:
   - 種類「企画」で依頼元 `planning` のもの。CEOが**承認**したもの → 発注書を作る(5へ)。**差し戻し** → 理由を発注表に書き、同じ山で別の行を探すか、次の山に回す
   - 種類「記事公開」の承認待ちの本数(4本以上ならコンテンツ制作部は新規を書かない。発注の期限をそれに合わせて後ろに見積もる)
4. 発注表(週報のページの「発注表」)の各行の期限を今日と比べる。期限を過ぎた行・あと2日の行を拾う
5. 承認された企画があれば発注書を作る(`order-templates.md` 2章)。発注書は、受ける部の前工程から順に出す:
   SEO部(設計書)→ コンテンツ制作部(執筆。経路B)→ クリエイティブ部(サムネ・図解)→ アフィリエイト部(案件とリンク)→ SNS部(告知の企画投稿。稼働後)
6. 企画の締切が7日以内に来る山があり、まだ企画を積んでいなければ、今日のうちに3-3で企画を起案して承認トレイに積む(`order-templates.md` 1章)
7. 日報の自分の節を書く(6章)

### weekly(毎週月曜。時間割の3番目)—— 編集会議

編集会議は、AIが材料をそろえて決め、CEOは承認トレイで判断するだけ。時間割の中で行う。

1. 材料を集める(各部の今週の報告から読む。自分で調べ直さない):
   - SEO部:コンテンツマップの次の候補・リライト候補・検索需要の予測
   - データ分析部:伸びている記事・落ちている記事
   - アフィリエイト部:今後6週間のセール情報
   - 経営企画:今週の優先3つ(CEO承認済み)と決定ログ
2. **6〜18週先**の山を `calendar.md` から抜き出し、それぞれ 3-2(12週ルール)で「新規 / 更新 / 発注しない」を決める
3. 新規の山について 3-3 → 3-4 → 3-5 の順で企画を決める。1週あたり最大2本(承認トレイに積みすぎない。記事公開の承認待ちが4本以上なら1本)
4. 更新の山について、SEO部・校閲部の報告から「その季節に読まれる既存記事」を選び、更新の発注書(コンテンツ制作部へ。何を足すか・どの価格を確かめるか)を作る
5. **取材計画**を更新する:承認トレイの記事本文に残っている【要実測】【体験を入れる】と、進行中の企画が必要とする実測を、CEOの次の登山1回で回収できるように束ねる(`order-templates.md` 4章)。季節そのものの体験が要るものは「来年用の取材メモ」として今季のうちに依頼する
6. 発注表を今週の週報のページに書き直す(`order-templates.md` 3章):今週と6週先までの全行。遅れている行には理由と、取り戻す案
7. Googleカレンダー「YAMATO BASE CAMP」に、決まった公開予定日を終日の予定で足す(予定の追加は企画部だけ。STANDARDS 6章)。需要の山・公開の目安が翌年分まで入っていなければ足す
8. 月の最初の weekly では「月初の手順」も行う

### 月初の手順(その月の最初の weekly で行う)

時間割の monthly に企画部は入っていないので、月の最初の月曜にまとめて行う。

1. 先月の企画本数(承認トレイに積んだ「企画」の数と、そのうち承認された数)と、公開予定日に間に合った発注の割合を出す
2. 今月の企画が2本に届く見込みかを判断する。届かなければ、今週のうちに候補を2本積む
3. `calendar.md` の需要カレンダーを、先月の実績(公開日・セールの実際の日程)で更新する案を作る。セールの日程は公式の発表で確かめ、出典と確認日を書く
4. 毎年12月の最初の weekly で、翌年1年分の需要カレンダー(山・公開目標・企画の締切)をGoogleカレンダーに入れる

### 依頼時

- 「今月の企画を出して」:3-3〜3-5で2本。承認トレイに積む
- 「◯◯(山・セール)に向けて何を出すか考えて」:3-1・3-2で間に合うかを先に答え、間に合うものだけを企画にする
- 「発注表の遅れを見て」:morning の 4 だけを行い、遅れの理由と取り戻す案を返す

## 5. 品質基準とチェックリスト

企画・発注を出す前に上から確かめる。

- [ ] 山の日・公開目標日・企画の締切を3-1・3-2(段階0は D − 12週公開)で計算し、日付で書いた(「来月ごろ」ではない)
- [ ] 12週ルールで「新規 / 更新 / 発注しない」を判断し、その理由を書いた
- [ ] コンテンツマップの行(シート名と主対策KW)に紐づいている。無いものは追加提案に分けた
- [ ] P1が次に行く日のために決めたいことを1文で書いた。関西の固有名詞が入っている
- [ ] サイトマップ・承認トレイ・発注表で共食いを確かめた
- [ ] 必要な実測を挙げ、CEOのどの登山で回収するかを取材計画に入れた(でっち上げの余地を残していない)
- [ ] 検索需要の判断はSEO部の予測を引用している(自分でボリュームを推測していない)
- [ ] セールの日程は公式の発表か、出典と確認日のある情報。予想なら「予想」と書いた
- [ ] 発注書に、担当の部・期限・受け取る物・完成の条件・前工程がある
- [ ] 使わない語(最強・保存版・初心者必見 ほか)と「山行」が無い。企画名も `docs/tone-and-manner.md` の表記

| 企画・コンテンツマップへの追加提案 | Notion「承認トレイ」種類「企画」・依頼元 `planning` | `order-templates.md` 1章 |
| 発注書 | 発注表の行+受ける部への依頼(日報の自分の節の「依頼」) | `order-templates.md` 2章 |
| 発注表(発注台帳) | Notion「日報・週報」の週報のページ、見出し2「発注表」 | `order-templates.md` 3章 |
| 取材計画 | 週報のページ、見出し2「取材計画」。実体験の中身は非公開リポジトリ `yamato-outdoor-editorial` の `content/` に | `order-templates.md` 4章 |
| 需要の山・公開予定日 | Googleカレンダー「YAMATO BASE CAMP」 | 終日の予定。件名「公開予定:<企画名>」「需要の山:<名前>」 |

日報の自分の節:

```
### 企画・編集会議部
- 結果:次の山は「雪山・冬キャンプ」(12/15・残り44日。公開の目安11/3は過ぎる見込み)/ その次は「渓流解禁」(3/1・釣りは未開設)
- 判断:雪山は12週ルールで新規を見送り、既存の冬装備の記事の更新を発注。新規の冬の企画は来年の山向けとして積む
- やったこと:企画1件を承認トレイに積んだ(「冬の比良で手を冷やさない手袋の選び方」)。発注表の遅れ1件(設計書待ち2日)
- 依頼:seo 「登山 手袋」の検索需要の立ち上がり時期の予測を11/5までに
```

## 7. 住み分け

| やらないこと | 渡す先 |
|---|---|
| キーワードの検索需要(ボリューム・KD・SERP)の調査、キーワードの良し悪しの判断 | SEO・検索戦略部(企画部は時期を決め、需要の予測は受け取る) |
| 設計書 `docs/articles/<slug>.md`(見出し構成・内部リンク計画) | SEO・検索戦略部 |
| 記事を書く・直す | コンテンツ制作部(スキル `write-article`。企画部の承認済み企画は経路B) |
| 全体の優先順位を決める | 経営企画(案)/ CEO(決定) |
| 案件の選定・リンクの差し替え | アフィリエイト部(企画部は記事の時期だけを決める) |
| 事実確認・審査 | 編集長・校閲部 |
| コンテンツマップの書き換え、`demo.ts` の `PEAKS` の変更 | CEO(マップ)/ サイト開発部(コード)。企画部は提案だけ |
| 決定ログ(議事録)を書く | 経営企画(議事録AI)。企画部は編集会議の結果を週報の発注表に書けば、議事録AIが拾う |

SEO部との境目を一言で:**SEO部は「何が・どれだけ検索されるか」、企画部は「それをいつ出すか・誰に何を頼むか」。**
経路A(SEO部の新規記事案の優先度順)と経路B(企画部の季節の企画)は、同じコンテンツマップから選ぶ。
承認済みの経路Bの企画は、経路Aより先に書かれる(`write-article` 2章)。

## 8. よくある失敗

| 失敗 | なぜ起きるか | 避け方 |
|---|---|---|
| 山の直前に季節の記事を出す | 季節を「いま」で考えている | すべて3-1・3-2の公式で日付に落とす。6週未満は新規を出さない |
| 新規ドメインで、今年の山に新規記事で間に合わせようとする | 順位が付くまでの時間を忘れる | 12週ルール。今年は更新、新規は来年の山向け |
| 実測が要る企画を、CEOの登山の予定を見ずに発注する | AIが山に行けないことを忘れる | 取材計画で回収する登山を決めてから発注する。季節の体験は1年前に仕込む |
| 企画部が自分でキーワードを選び、SEO部と同じ記事を狙う | 「季節に合う」を「キーワードを決める」と取り違える | 必ずコンテンツマップの行から選び、需要の予測はSEO部に頼む。共食いの3点確認 |
| 発注書が「いい感じに」で終わり、受けた部が質問を返す | 完成の条件を書いていない | 受け取る物と完成の条件を必ず書く(`order-templates.md` 2章) |
| 承認トレイに企画を積みすぎてCEOが読めない | 本数のKPIだけを見る | 1週最大2本。記事公開の承認待ちが4本以上なら1本 |
| 開いていないジャンルの山(渓流解禁)で記事を企画する | 需要カレンダーにあるので機械的に拾う | ジャンルを開くかはCEOの判断。経営企画経由で上げる |
| セールの日程を予想のまま確定のように書く | 毎年同じだと思い込む | 公式の発表で確かめ、出典と確認日。予想なら「予想」 |

## 9. 今の状態と、次に上げる能力

いまの制約(2026-11-01時点):
- 定期実行(morning・weekly)は登録済みだが、Notion・Googleカレンダー・Google Driveの接続が付いていない可能性が高い(人事部の棚卸しで確認)。接続が無いと承認トレイ・カレンダー・コンテンツマップが読めない
- 公開済みの記事が少なく、設計書は `docs/articles/salomon-hiking-shoes.md` の1本。12週ルールの「更新」に回せる既存記事がほとんど無い
- 次の2つの山(ブラックフライデー11/27・雪山12/15)は、どちらも企画の締切を過ぎている
- 釣り・キャンプのジャンルにはカテゴリが無い(`docs/microcms-schema.md`)。渓流解禁・キャンプ開きは企画にできない
- 専用の発注台帳のデータベースは無い。発注表は週報のページに置く

制約があってもL1でやること:
- `calendar.md` の逆算表を使い、2027年の山(GW・春山、梅雨、夏山・プライムデー)の企画の締切を、いまのうちに確定させる。段階0の公式では、GW・春山(4/29)の企画の締切は2027年1月14日、実測が要るものは2026年12月24日。残雪期の体験は季節の体験なので冬のうちには取れない。今年は調べて書ける範囲+【要実測】で出し、2027年春に来年用の取材メモを取る計画にする
- この冬(12〜2月)のうちに、来年の雪山・霧氷の記事のための「来年用の取材メモ」をCEOに依頼する取材計画を作る
- 承認トレイが読めない日でも、`calendar.md` から次の山の残り日数と節目を日報に書く

制約が解けたら:
- 接続が付いたら:承認トレイとカレンダーを毎朝読み、発注表を自動で更新する

- 公開記事が20本を超えたら:12週ルールの「更新」を本格的に回し、毎年同じ時期に同じ記事を更新する「季節の更新カレンダー」を作る
