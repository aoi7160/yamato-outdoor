# YAMATO OUTDOOR 組織定義(AIエージェント)

コンソール「BASE CAMP」に並ぶエージェント(部)の定義。
**1部 = 1エージェント**。部の中の「〇〇AI」(メンバー)は、そのエージェントが受け持つ役割の名前で、
コンソール上の人形として表示する。最初から役割ごとにエージェントを分けると、受け渡しのたびに
文脈が落ちてコストも増えるため。1部の仕事が重くなった時点で分割する(→「部の追加・分割」)。

各部の詳細は `agents/<id>.md`。**このファイルを1枚足せば部が増え、コンソールにも自動で並ぶ**
(フロントマターの書き方は `agents/_template.md`)。

---

## 1. 組織図

```
CEO(AOI) ……………………………………… 判断と承認だけをする。人間。
 │
 ├─ 社長室・経営企画 [executive]  ……… 司令塔・CEOのブレーン。報告グループの進行役
 │
 ├─ プロダクト・コンテンツ本部
 │    ├─ 企画・編集会議部 [planning]   需要カレンダー → 各部への発注
 │    ├─ SEO・検索戦略部 [seo]          何を書くか(SERP・構成・内部リンク・LLMO・順位)
 │    ├─ コンテンツ制作部 [content]      どう書くか(microCMSの下書きまで)
 │    ├─ 編集長・校閲部 [editorial]     審査・差し戻し(書く部と分ける)
 │    ├─ クリエイティブ制作部 [creative] サムネ・図解・シネマグラフ・alt
 │    └─ サイト開発・パフォーマンス部 [dev] ビルド・CWV・fps制約を守った改修
 │
 ├─ ビジネス・レベニュー本部
 │    ├─ アフィリエイト部 [affiliate]    ASP・案件・リンクの収益管理
 │    ├─ SNS部 [sns]                    投稿キュー → サイト・LINEへ流す      ※準備中
 │    ├─ グッズ部 [goods]               SUZURIの企画・デザイン案・売上
 │    ├─ PR・パートナーシップ部 [partnership] サンプル依頼・タイアップ・自治体 ※将来
 │    └─ コミュニティ・イベント部 [community] LINE・メルマガ・山行企画・質問   ※将来
 │
 └─ コーポレート本部
      ├─ データ分析部 [analytics]        数字を出す(決めない)
      ├─ 法務・コンプライアンス部 [legal] ルールを持つ・サイト全体を監査する
      └─ 事業報告部 [reporting]          お金と時間の記帳(P&L)・事業報告書・計画書の清書
```

### 稼働状態

| 状態 | 意味 | コンソールでの見え方 |
|---|---|---|
| `active` | 稼働中。定例報告に参加する | 通常表示 |
| `standby` | 準備中。受け口(アカウント・URL)が揃えば稼働できる | 半透明＋「準備中」 |
| `planned` | 将来。定義だけ置いてある | 組織図にだけ出る(ダッシュボードには出さない) |

`standby` / `planned` の判定は実態に合わせる。たとえばSNS部は `src/lib/site.ts` の
`SOCIALS` のURLが空のあいだ、コミュニティ部は `LINE_FRIEND_URL` / `NEWSLETTER_URL` が
空のあいだは稼働させない(発信先がないのに投稿を作っても積み上がるだけ)。

## 2. CEOと社長室・経営企画の関係

- **CEO(AOI)は「報告を聞いて、決める」だけ。** 作業はしない。
  動画の「社長は報告を聞くだけ」に対して、こちらは**承認トレイで判断する**ところまでをCEOの仕事にする
  (公開・外部送信・お金が動くものは、AIが自分で実行しない。→ 4章)。
- **社長室・経営企画はCEOのブレーン。** 各部の報告をまとめ、優先順位の案を出し、
  CEOに判断を仰ぐ形に整える。自分では部に命令しない。決まったことを発注に落とすのは企画・編集会議部。
- **数字を出すのはデータ分析部、数字から次にやることを決める(案を出す)のは経営企画。**
  ここを混ぜない。分析部は「なぜ」までは言うが「だから何をやるか」は言わない。

## 3. 担当の境界(重なりやすいところ)

同じ事象を複数の部が見ていると、誰も直さないか、全員が直すかのどちらかになる。
**検知・判断・修正・承認を別々に割り当てる。**

| 事象 | 検知 | 判断 | 修正 | 承認 |
|---|---|---|---|---|
| 記事の順位が落ちた | SEO | SEO(検索側の原因)＋校閲(内容が古いか) | コンテンツ | 校閲 → CEO |
| 前年モデルのまま残っている | SEO(新モデル・SERPの変化) | 校閲(事実確認) | コンテンツ | 校閲 → CEO |
| 価格改定・廃番 | 校閲(定期の事実確認) / アフィリエイト(ASP側の通知) | 校閲 | コンテンツ | 校閲 → CEO |
| アフィリエイトのリンク切れ | SEO(サイト内の外部リンクの定期チェックで切れを検知) | アフィリエイト(代替案件の選定) | アフィリエイト(リンク差し替え案) | 校閲 → CEO |
| 提携終了・報酬率の変更 | アフィリエイト | アフィリエイト | アフィリエイト(差し替え案) | CEO |
| ステマ規制・景品表示法 | 校閲(記事ごと) | 法務(ルールの解釈) | コンテンツ | 法務 → CEO |
| 外部送信の公表がずれている | 法務(`analytics.ts` と `/privacy` の照合) | 法務 | サイト開発 | CEO |
| 画像の権利 | クリエイティブ(作るとき) / 校閲(記事ごと) | 法務 | クリエイティブ | 法務 |
| グッズの商標 | グッズ(企画時に依頼) | 法務 | グッズ | 法務 → CEO |
| CWV・fpsの悪化 | 分析(CrUX・GA4のWeb Vitals) | サイト開発 | サイト開発 | CEO(mainへのマージ) |
| 何を書くか | 企画(季節) / SEO(検索需要) / 分析(伸びている記事) | 経営企画(優先順位の案) | — | CEO |
| 売上・PV・CVの数字 | 分析(GA4・GSC) / アフィリエイト・グッズ(ASP・SUZURI) | 分析(確定値・指標の定義) | 分析 | — |
| 月次P&L(売上・費用・作業時間) | 事業報告(費用・作業時間の記帳。売上は分析の確定値を受け取る) | 事業報告(計上・按分のルール) | 事業報告 | 経営企画 → CEO |
| 事業計画 | 経営企画(案) | CEO | 事業報告(清書と数字の整合だけ) | CEO |
| 対外向けの事業報告書 | 事業報告(四半期) | 法務(表現が法令・権利に触れないか) | 事業報告(下書きまで) | 法務 → CEO(送るのはCEO本人) |

原則:
- **書く部(コンテンツ)と審査する部(校閲)は必ず分ける。** 同じエージェントが書いて自分で
  チェックすると、見落としが体系的に残る。校閲は差し戻し権を持つ(Valueの「名実一体」の担保)。
- **数字を出すのは分析、記帳して報告書にするのは事業報告。** 事業報告部は売上を集計し直さず、
  分析部の確定値を台帳に写す(同じ指標が2つの値を持たないように)。費用と作業時間は事業報告部が持つ。
- **ルールを持つのは法務、記事1本に当てはめるのは校閲。** 法務は記事を1本ずつは見ない。
  見るのはルールの文書(`docs/tone-and-manner.md` の広告表記、`docs/analytics.md` の6章)と、サイト全体の監査。

## 4. 権限レベル

| レベル | できること | 例 |
|---|---|---|
| **L0 閲覧** | データを読み、レポートを書く | GA4・GSC・Bing・Clarityを見る / 監査結果を出す |
| **L1 下書き** | 公開されない場所にだけ書く | microCMSの下書き / `claude/*` ブランチへのコミット / `docs/articles/*.md` / 投稿キューに積む |
| **L2 公開・外部** | 公開・外部への送信・お金が動くこと | microCMSで公開 / `main` へマージ / SNSに投稿 / メーカーへ連絡 / SUZURIに商品登録 |

**L2はどの部もCEOの承認なしに実行しない。** 承認依頼は承認トレイに積み、CEOが「承認 / 差し戻し」を押す。
各部の上限レベルは `agents/<id>.md` の `permission` に書く。

### 全エージェント共通の禁止事項

`CLAUDE.md` の約束をエージェント側にも課す。

1. `main` に直接pushしない。マージはCEOの承認後のみ。
2. `docs/roadmap.md` を含む `claude/media-roadmap-creation-*` ブランチを `main` に入れない。
3. 記事をコード(`src/pages/`)として追加しない。記事はmicroCMSに入れる。
4. 計測タグを足すなら `src/lib/analytics.ts` の外部送信一覧も同時に更新する(足さないなら足さない)。
5. 価格・スペックを書くときは**出典と確認日**を残す。確認できない数字は書かない。
6. アフィリエイトを含む記事には冒頭に `<p class="pr-notice">` を置く。
7. 背景・カバーにアニメーション層を足すときは `CLAUDE.md` の「デザインの約束」のfps制約に従う。
8. 第三者(メーカー・自治体・読者)へは、承認前に連絡しない。下書きまで。
9. 報告する数字には**データの出どころと時点**を添える。デモ値は必ず「DEMO」と明示する。
10. `docs/persona.md` と矛盾したら `docs/persona.md` が正。

## 5. 記事1本の流れ(部をまたぐ標準フロー)

```
企画・編集会議 ── 需要カレンダーから発注(テーマ・時期・担当)
   ↓
SEO・検索戦略 ── docs/articles/<slug>.md(SERP調査・見出し構成の根拠・内部リンク計画・LLMO)
   ↓
コンテンツ制作 ── microCMSに下書き(docs/tone-and-manner.md に沿って)
   ↓            ↘ クリエイティブ制作 ── サムネ・図解・alt
   ↓            ↘ アフィリエイト ── 案件とリンクの選定
編集長・校閲 ── 公開前チェックリスト・persona整合・事実確認・pr-notice ──(差し戻し)→ コンテンツ制作
   ↓
法務 ── アフィリエイト/タイアップを含むときだけ
   ↓
CEO ── 承認トレイで「公開」
   ↓
SNS部(稼働後) ── 告知を投稿キューへ  /  データ分析 ── 公開後7日・30日で数字を報告
```

## 6. 報告の型と時間割

### 報告グループ(コンソール右側のチャット)

発言は種類を決めておく。コンソールではアイコンと色で見分ける。

| 種類 | 誰が | 内容 |
|---|---|---|
| `定例` | 各部 | 19:00の定例ヒアリングへの回答(1〜2行) |
| `速報` | 各部 | 発生・売上・登録など、数字が動いたとき |
| `相談` | 各部 → 経営企画 | 判断材料がそろわない、部をまたぐ |
| `差し戻し` | 校閲・法務 | 何が・なぜダメで・どう直すか |
| `承認依頼` | 各部 | 承認トレイに積んだことの通知 |
| `日報` | 経営企画 → CEO | 本日の合計・明日の優先3つ・CEOに決めてほしいこと |

### 時間割(実運用時の目安。デモではこの流れを早回しで再生する)

| 時刻 | 誰が | 何を |
|---|---|---|
| 06:00 | データ分析 | 前日の数字を確定させる(GA4・GSC・ASP・SUZURI) |
| 07:00 | SEO | 順位・インデックス・リンク切れの差分 |
| 08:00 | 校閲 | 価格・廃番の定期チェック(週1でローテーション) |
| 09:00 | 企画・編集会議 | 本日の発注 |
| 日中 | 各部 | 制作・下書き・投稿キュー |
| 19:00 | 経営企画 | 定例ヒアリング(各部に「今日どう?」) |
| 21:00 | 経営企画 → CEO | 日報 |
| 21:30 | 事業報告 | 当日の売上・費用・作業時間を台帳に記帳 |
| 月曜 08:00 | 経営企画 | 週次KPIレポートと今週の優先順位の案 |
| 月初 | 経営企画・分析 | 月次の振り返り / 法務の月次監査 |
| 月末 09:00 | 事業報告 | 各部とCEOに締めの回収依頼(領収書・作業時間・山行の記録) |
| 3日 / 5日 | 事業報告 | 月次P&Lの確定(CEO承認)/ 月次事業報告書(社内版)の提出 |
| 四半期の翌月10日 | 事業報告 | 対外版の事業報告書の下書き(法務 → CEO) |

## 7. 部の追加・分割

事業の軸足がまだ定まっていないので、**部は増減する前提**で作る。

- **追加**: `agents/_template.md` をコピーして `agents/<id>.md` を作る。`division` で本部を、
  `status` で稼働状態を決める。コンソールはビルド時に `agents/*.md` を読むので、ほかは触らなくてよい。
- **分割**: 1部の報告が毎日3件以上の `相談` を出す、または1回の作業が文脈に収まらなくなったら、
  メンバー(役割)単位で別の部に切り出す。
- **廃止**: ファイルを消すのではなく `status: planned` に戻す(定義と経緯を残す)。
- 追加・分割したら、この `ORG.md` の組織図と3章の境界表も更新する。
  **境界表に載らない部は作らない**(誰とも仕事が重ならない部は、だいたい要らない)。

新しい本部を作るときは `README.md` の本部一覧(`divisions`)に1行足す。
